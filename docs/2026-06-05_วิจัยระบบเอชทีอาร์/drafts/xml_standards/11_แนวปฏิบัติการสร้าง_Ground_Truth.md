## 1. Ground Truth (GT) คืออะไร และทำไมถึงสำคัญต่อโมเดล HTR

### 1.1 นิยามและความหมายพื้นฐานของ Ground Truth
Ground Truth (GT) ในบริบทของการจดจำอักษรด้วยปัญญาประดิษฐ์ (AI) ไม่ว่าจะเป็น OCR (Optical Character Recognition) สำหรับเอกสารพิมพ์ หรือ HTR (Handwritten Text Recognition) สำหรับเอกสารตัวเขียนอักษรย่อ หมายถึง **"ข้อมูลสอน (Training Data) คุณภาพสูง"** ข้อมูลเหล่านี้ต้องเกิดจากกระบวนการที่มนุษย์เป็นผู้สร้างขึ้นหรือตรวจสอบความถูกต้องอย่างละเอียดแล้ว ข้อมูล Ground Truth ทำหน้าที่เป็น "ความจริงสูงสุด" หรือมาตรฐานอ้างอิง (Gold Standard) ที่ใช้สอนปัญญาประดิษฐ์ให้เข้าใจว่า รูปภาพที่ปรากฏบนหน้ากระดาษในแต่ละพิกัด หรือกลุ่มของพิกเซลที่มีหมึกเปื้อนอยู่นั้น ตรงกับตัวอักษรใดในระบบคอมพิวเตอร์ (เช่น มาตรฐาน Unicode)

ในทางปฏิบัติ การสร้าง Ground Truth ไม่ได้หมายถึงการพิมพ์ข้อความเฉยๆ แต่ประกอบไปด้วยกระบวนการ 2 ส่วนหลักที่ต้องทำควบคู่กัน ได้แก่:
1. การทำโครงสร้างข้อมูลทางกายภาพ (Physical Layout Annotation): การตีเส้น (Baseline) หรือการกำหนดพื้นที่ (Polygon) รอบข้อความ
2. การถอดความเนื้อหา (Text Transcription): การพิมพ์ตัวอักษรให้ตรงกับภาพที่อยู่ในพื้นที่ที่กำหนดไว้ในข้อ 1

### 1.2 วัตถุประสงค์ของการสร้างข้อมูลสอน (Training Data)
วัตถุประสงค์หลักและสำคัญที่สุดของการจัดทำ Ground Truth คือการ **สร้างข้อมูลสอน (Training Data) คุณภาพสูงให้ AI (HTR/OCR Models)** 
ในกระบวนการเรียนรู้แบบมีผู้สอน (Supervised Learning) โมเดล AI จะเริ่มต้นจากสถานะที่ไม่รู้อะไรเลย มันต้องการตัวอย่างจำนวนมากเพื่อหาสถิติและความน่าจะเป็นของลวดลายหมึก เมื่อเราป้อน Ground Truth ที่มีคุณภาพเข้าไป โมเดลจะนำภาพไปผ่านเครือข่ายประสาทเทียม (Neural Networks) และเทียบผลลัพธ์การทำนายกับ Ground Truth เพื่อคำนวณหาค่าความสูญเสีย (Loss function) และปรับค่าน้ำหนัก (Weights) ให้ผลลัพธ์เข้าใกล้ Ground Truth มากที่สุด

### 1.3 ความสำคัญต่อความแม่นยำของโมเดล HTR
สำหรับเอกสารตัวเขียนด้วยมือ (Handwritten) หรือเอกสารโบราณที่มีความเสียหายตามกาลเวลา ความผันแปรของลายมือ (Handwriting Variability) มีสูงมาก ผู้เขียนแต่ละคนอาจเขียนตัวอักษรเดียวกันด้วยรูปร่างที่ต่างกันโดยสิ้นเชิง 
ความสำคัญของ Ground Truth ต่อ HTR จึงมีมากกว่า OCR ปกติหลายเท่า:
- ช่วยให้ AI แยกแยะการเขียนติดกัน (Cursive writing) ได้
- ช่วยให้ AI เรียนรู้การบิดเบี้ยวของบรรทัดที่ไม่ได้เขียนเป็นเส้นตรง
- เป็นจุดอ้างอิงที่สำคัญที่สุดสำหรับการประเมินโมเดลผ่านค่า Character Error Rate (CER) และ Word Error Rate (WER)

### 1.4 ปรากฏการณ์ Garbage In, Garbage Out ในบริบทของ AI
หากข้อมูล Ground Truth ที่ใช้สอนมีข้อผิดพลาด (เช่น วาดเส้นเบี้ยว ถอดความผิด สะกดผิด) โมเดลที่ถูกฝึกสอนออกมาก็จะมีข้อผิดพลาดตามไปด้วยโดยหลีกเลี่ยงไม่ได้ ปรากฏการณ์นี้เป็นที่รู้จักกันดีในวงการวิทยาการคอมพิวเตอร์ว่า "Garbage In, Garbage Out" (ขยะเข้า ขยะออก) 
การทุ่มเทเวลาให้กับการสร้าง Ground Truth ที่มีคุณภาพ 1,000 หน้า อาจให้ผลลัพธ์ที่ดีกว่าการใช้ข้อมูลที่ไม่มีคุณภาพ 10,000 หน้าเสียอีก

### 1.5 ภาพรวมของวงจรการพัฒนาชุดข้อมูล
ในวงจรการพัฒนา AI ด้าน HTR ข้อมูล Ground Truth จะถูกแบ่งออกเป็น 3 ชุด:
- Training Set: ข้อมูลก้อนใหญ่ที่สุด ใช้สำหรับสอนโมเดล
- Validation Set: ใช้ทดสอบระหว่างการสอน เพื่อป้องกันไม่ให้โมเดลจำข้อสอบ (Overfitting)
- Test Set: ข้อมูลชุดสุดท้ายที่ไม่เคยให้โมเดลเห็นมาก่อน ใช้สำหรับวัดผลประสิทธิภาพที่แท้จริง

## 2. กฎทองคำของการวาด Baseline

Baseline หรือเส้นบรรทัดฐาน เป็นแกนกลางและองค์ประกอบที่สำคัญที่สุดในระบบ HTR สมัยใหม่ โมเดล HTR ชั้นนำ (เช่น Kraken, Calamari) อาศัยวิธีการแบบ **Baseline-based segmentation แทน Box-based** เพื่อหลีกเลี่ยงปัญหาการทับซ้อนและเพิ่มความแม่นยำ

### 2.1 ทิศทาง (Directionality) จากซ้ายไปขวา
ทิศทางของการลากเส้น (Directionality) ถือเป็นปัจจัยที่โมเดลใช้ในการตัดสินลำดับก่อนหลังของตัวอักษร
- **กฎ:** สำหรับภาษาไทยและภาษาตะวันตก การลากเส้นต้องเริ่มต้นจากจุดซ้ายสุดของตัวอักษรตัวแรก ไปยังจุดขวาสุดของตัวอักษรตัวสุดท้ายในบรรทัดนั้นๆ **(ลากจากซ้ายไปขวาเสมอ)**
- หากผู้ทำ Ground Truth ลากเส้นจากขวาไปซ้าย (โดยไม่ตั้งใจ) โมเดลจะตีความว่าตัวอักษรทางขวาสุดคือตัวอักษรตัวแรกของบรรทัด ทำให้ผลลัพธ์การอ่านกลับด้านทั้งหมด

### 2.2 ตำแหน่งการจัดวางที่ใต้ตัวอักษรฐาน (Base character)
ตัวอักษรในภาษาไทยและภาษาอื่นๆ มีแกนหลักที่เรียกว่า Base character
- **กฎ:** การวาดเส้น Baseline จะต้องลากให้อยู่ด้านใต้ของตัวอักษรฐานเสมอ
- เส้นจะต้องสัมผัสหรืออยู่ใกล้กับส่วนล่างสุดของตัวอักษรฐานมากที่สุด (เช่น ใต้พยัญชนะ ก, ข, ค, ง)
- หากข้อความในบรรทัดมีการเขียนโค้งขึ้นหรือโค้งลง เส้น Baseline ก็ต้องถูกดัดให้โค้งตาม (Polygon-based Baseline) เพื่อให้ขนานกับข้อความ

### 2.3 การหลีกเลี่ยงสระล่างและหางพยัญชนะ
นี่คือจุดที่เกิดความผิดพลาดบ่อยที่สุดในการทำ Ground Truth เอกสารภาษาไทย
- **กฎ:** เส้น Baseline จะต้อง **ไม่** ลากอ้อมลงไปคลุมสระล่าง (เช่น สระอุ ุ, สระอู ู) หรือหางของพยัญชนะที่ลากยาวลงมาด้านล่าง (Descenders)
- เส้น Baseline ควรจะลากตัดผ่านทะลุหางเหล่านั้นไปเลยโดยรักษาระดับแนวระนาบของตัวอักษรฐานเอาไว้
- โมเดล HTR สมัยใหม่มีความสามารถในการเรียนรู้ได้เองว่า เมื่อมันเห็นเส้น Baseline ตรงๆ หากมีหมึกห้อยอยู่ข้างใต้ มันคือสระล่างหรือหางของอักษร

### 2.4 กรณีศึกษา: พยัญชนะไทยที่มีหางยาวและสระล่าง
ภาษาไทยมีตัวอักษรที่ต้องระมัดระวังในการวาด Baseline เป็นพิเศษ:
1. **พยัญชนะที่มีหางยาวลงล่าง:** ฤ, ฤๅ, ญ, ฐ
2. **พยัญชนะที่บางครั้งผู้เขียนลากหางยาวลงมา:** ป, ฝ, ฟ (ในเอกสารโบราณบางยุค อาจเขียนหางชี้ลงล่าง)
3. **สระล่าง:** สระอุ (ุ), สระอู (ู), พินทุ (ฺ)

ตารางด้านล่างแสดงการตัดสินใจในการวาด Baseline สำหรับตัวอักษรเหล่านี้:

| ตัวอักษร/คำในต้นฉบับ | การวาด Baseline ที่ถูกต้อง | การวาดที่ผิดพลาด |
| :--- | :--- | :--- |
| คำว่า "ผู้หญิง" | ลากเส้นตรงใต้ตัว ญ โดยตัดผ่านฐานของ ญ ไปเลย | หักเส้นลบลงไปใต้ฐานของ ญ แล้วหักขึ้นมาใหม่ |
| คำว่า "ประเสริฐ" | ลากเส้นตรงใต้ตัว ฐ โดยตัดผ่านฐานของ ฐ | หักเส้นหลบลงไปใต้ฐานของ ฐ ทำให้เส้นคดเคี้ยว |
| คำว่า "ความรู้" | ลากเส้นตรงใต้ตัว ร โดยตัดผ่านสระอู (ู) | หักเส้นหลบสระอู ทำให้ระดับบรรทัดเสียรูป |
| คำว่า "ภาษาอังกฤษ" | ลากเส้นตรงใต้ตัว ก, ฤ, ษ โดยตัดผ่านหางของ ฤ | วาดเส้นขรุขระตามรอยหยักของหาง ฤ |

### 2.5 ผลกระทบของการวาด Baseline ผิดพลาด
หากผู้วาด Ground Truth ละเมิดกฎทองคำเหล่านี้ จะส่งผลกระทบอย่างร้ายแรงต่อกระบวนการ Training:
1. **เส้นคดเคี้ยว (Wavy Baseline):** หากพยายามหักหลบสระล่าง โมเดลจะสับสนและพยายามบิดภาพ (Image warping) ตามเส้นที่คดเคี้ยว ทำให้ภาพตัวอักษรผิดเพี้ยนไปก่อนที่จะถูกส่งเข้า Neural Network
2. **สลับบรรทัด (Line Skipping):** หากลากเส้น Baseline ของบรรทัดบนต่ำเกินไปจนไปทับสระบนของบรรทัดล่าง โมเดลอาจดึงเอาข้อความของบรรทัดล่างมาปะปนกับบรรทัดบน

## 3. กฎทองคำของการกำหนดเขต (Polygon/Bounding Box)

การกำหนดเขต (Region Boundary) เป็นกระบวนการที่ทำควบคู่กับ Baseline เพื่อบอกว่า "พื้นที่พิกเซล" ใดบ้างที่เป็นของบรรทัดนั้นๆ [2]

### 3.1 ความแตกต่างระหว่าง Bounding Box และ Polygon
- **Bounding Box (กล่องสี่เหลี่ยมผืนผ้า):** ใช้แกนพิกัดเพียง 4 มุม (Top-Left, Width, Height) วาดง่าย รวดเร็ว มักใช้ในรูปแบบ ALTO XML หรือข้อมูลเอกสารพิมพ์ที่บรรทัดห่างกันมากๆ
- **Polygon (รูปหลายเหลี่ยม):** ใช้จุดพิกัด (Points) จำนวนมากมาต่อกันเป็นรูปร่างใดๆ ก็ได้ มีความยืดหยุ่นสูง สามารถซอกซอนเข้าไปหลบหลีกสิ่งกีดขวางได้ 

**แนวทางแก้ไข (Best Practices):** "ใช้ PAGE XML Polygon แทน ALTO Bounding Box เพื่อเลี่ยง Overlap" เป็นกฎที่สำคัญมากสำหรับเอกสารภาษาไทย

### 3.2 กฎการครอบคลุมทุกจุดพิกเซล (Full Pixel Coverage)
- **กฎ:** Polygon จะต้องครอบคลุมทุกจุดพิกเซลของข้อความในบรรทัดนั้น รวมสระบนและสระล่างทั้งหมด
- ห้ามมีติ่งของสระ หางของพยัญชนะ หรือเครื่องหมายวรรคตอนใดๆ หลุดออกไปนอก Polygon 
- การกำหนดเขตที่แคบเกินไป (Tight box) จนไปตัดขอบตัวอักษร จะทำให้ภาพที่ถูก crop ออกมาแหว่ง และทำให้ AI สับสน

### 3.3 กฎการห้ามทับซ้อน (No Overlap) ระหว่างบรรทัด
ปัญหาใหญ่ที่สุดของการใช้ Bounding Box ในภาษาไทยคือการทับซ้อน (Overlap)
- ภาษาไทยมี 4 ระดับอักษร: ระดับเหนือวรรณยุกต์ (เช่น ไม้โทบนสระอี), ระดับสระบน (เช่น สระอิ), ระดับพยัญชนะฐาน, ระดับสระล่าง (เช่น สระอุ)
- เมื่อบรรทัดสองบรรทัดเขียนชิดกัน สระบนของบรรทัดล่าง อาจทะลุขึ้นไปชนกับสระล่างของบรรทัดบน 
- **กฎ:** ห้ามทับซ้อนกับ Polygon ของบรรทัดอื่นเด็ดขาด ผู้วาดต้องใช้ Polygon เพิ่มจุดพิกัดดัดโค้งหลบหลีกกันเหมือนจิ๊กซอว์ 
- หากเกิด Overlap ภาพที่ตัดออกมาให้ AI จะมีตัวอักษรของบรรทัดอื่นติดมาด้วย (Noise) ทำให้โมเดลเรียนรู้ผิดพลาด

### 3.4 ระดับของการทำ Word Segmentation และข้อจำกัด
เครื่องมือหลายตัวรองรับการทำ Word Segmentation (การแยกคำ) โดยใช้แท็ก `<Word>`
- **ปัญหาหลัก:** ในภาษาไทย "ไม่มีช่องว่างระหว่างคำ" (No word spacing) การแยกคำในระดับพิกเซลจึงทำได้ยากและคลุมเครือ 
- การพยายามวาด Polygon แยกระดับคำจะส่งผลเสียต่อการเรียนรู้ของ HTR เพราะทำให้เกิดรอยต่อที่ไม่ธรรมชาติ
- **แนวทางปฏิบัติ:** กำหนดกฎการสร้าง Ground truth ระดับ TextLine เป็นหลัก ไม่ฝืนทำระดับ Word การวิเคราะห์ระดับคำปล่อยให้เป็นหน้าที่ของ Language Model (NLP) ในภายหลัง

### 3.5 เทคนิคการวาด Polygon สำหรับภาษาไทยที่มี 4 ระดับอักษร
1. เริ่มต้นจากการวาดสี่เหลี่ยมรอบบรรทัดแบบหลวมๆ
2. มองหาจุดที่สระบนหรือสระล่างชนกับบรรทัดอื่น
3. เพิ่มโหนด (Node/Point) ลงบนเส้นขอบของ Polygon แล้วดึงหลบหลีก
4. รักษาระยะห่างจากหมึก (Margin) ประมาณ 1-2 พิกเซล เพื่อความปลอดภัย

### 3.6 ตัวอย่างโครงสร้าง PAGE XML สำหรับ Polygon ที่ซับซ้อน
ในตัวอย่างนี้แสดง `<Coords>` ที่มีหลายจุดพิกัดเพื่อหลบหลีกบรรทัดที่ซ้อนทับกัน

## 4. กฎการถอดความ (Transcription Rules)

แม้จะวาดโครงสร้างสมบูรณ์แบบเพียงใด หากการถอดความ (Transcription) ผิดพลาด Ground Truth นั้นก็ไร้ความหมาย

### 4.1 ความหมายและหลักการของ Diplomatic Transcription
กฎทองคำของการถอดความคือแนวคิด **"Diplomatic Transcription"** (การถอดความตามรูปอักษร)
- **หลักการ:** พิมพ์สิ่งตาเห็น (What you see is what you get)
- เป้าหมายของการสร้าง HTR คือการทำให้ AI "อ่าน" สิ่งที่อยู่บนกระดาษ ไม่ใช่ "ตีความ" หรือ "แก้ไข" สิ่งที่อยู่บนกระดาษ
- ดังนั้น ผู้ทำ Ground Truth ต้องสวมบทบาทเป็นผู้คัดลอกที่ซื่อสัตย์ที่สุด ห้ามสวมบทบาทเป็นบรรณาธิการ (Editor) เด็ดขาด

### 4.2 การจัดการคำผิดในเอกสารต้นฉบับ
- **กฎ:** ผิดให้พิมพ์ผิด ห้ามแก้ไวยากรณ์ให้ถูกต้องเอง
- หากต้นฉบับเขียนว่า "ประเทษ" ผู้ถอดความก็ต้องพิมพ์ว่า "ประเทษ" ห้ามแก้เป็น "ประเทศ" เด็ดขาด
- การแก้คำผิดให้ถูกต้อง เป็นการใส่ Hallucination ลงไปใน Ground Truth เพราะภาพ (Feature) คือ "ษ" แต่ผู้สอนบอกว่ามันคือ "ศ" โมเดล AI จะสับสนอย่างหนัก

### 4.3 การถอดความอักษรโบราณ (Historical characters)
- **กฎ:** รักษาตัวอักษรโบราณ (Historical characters) เอาไว้ให้สมบูรณ์
- ในเอกสารภาษาไทยยุคเก่า อาจมีการใช้ตัวอักษรที่ไม่มีในปัจจุบัน หรือใช้สระในตำแหน่งที่แปลกไป เช่น การใช้ ฤ ฤๅ แทน ร หรือการใช้ตัวสะกดแปลกๆ
- การจัดการ Unicode: ต้องระวังปัญหา สระอำ (ำ) หรือ ญ ฐ ที่ไม่มีฐาน ต้องค้นหาและใช้รหัส Unicode ที่ถูกต้อง ไม่ใช่การประดิษฐ์ขึ้นมาเอง หรือทดแทนด้วยอักษรยุคปัจจุบัน

### 4.4 การจัดการคำย่อ (Abbreviations)
- **กฎ:** คำย่อ (Abbreviations) - พิมพ์ตามที่เห็น อย่าขยายคำย่อเอง
- หากต้นฉบับเขียน "กทม." ต้องพิมพ์ "กทม."
- ห้ามขยายเป็น "กรุงเทพมหานคร" เด็ดขาด เว้นแต่ในระดับการทำ TEI XML ที่อนุญาตให้ใช้ `<choice>` และ `<expan>` ได้ แต่ในระดับ PAGE/ALTO ที่ใช้สอน HTR ต้องยึดถือภาพเป็นหลัก

### 4.5 การจัดการเครื่องหมายวรรคตอนและการเว้นวรรค
- **กฎ:** เครื่องหมายวรรคตอน ต้องพิมพ์ให้ตรงกับต้นฉบับ
- หากมีจุด (.), จุลภาค (,), อัญประกาศ (") ก็ต้องพิมพ์ให้ครบถ้วน
- การเว้นวรรคในภาษาไทย: ภาษาไทยมักเขียนติดกัน แต่หากผู้เขียนต้นฉบับมีการตั้งใจเว้นวรรค (Space) อย่างชัดเจน ผู้ถอดความก็ควรพิมพ์เครื่องหมายเว้นวรรคลงใน `<Unicode>` ด้วย เพื่อให้โมเดลเรียนรู้โครงสร้างการเว้นวรรค

## 5. การจัดการองค์ประกอบที่ซับซ้อน (Complex Elements)

เอกสารที่แท้จริงไม่ได้มีแค่ข้อความเรียงกันเป็นย่อหน้า แต่ประกอบด้วยองค์ประกอบ (Layout elements) ที่หลากหลาย การกำหนด Region ให้ถูกต้องมีความสำคัญต่อกระบวนการ Document Layout Analysis (DLA)

### 5.1 การจัดการพื้นที่ตาราง (TableRegion)
- ตารางมีความซับซ้อนเพราะลำดับการอ่าน (Reading Order) ไม่ใช่ซ้ายไปขวาเสมอไป
- ต้องวาดเขตข้อมูลโดยใช้ประเภทที่รองรับตาราง (เช่น `<TableRegion>` ใน PAGE XML)
- ภายในตาราง อาจต้องกำหนดเซลล์ย่อย แล้วค่อยวาด TextLine เข้าไปในเซลล์นั้น
- อย่าลาก Baseline ข้ามคอลัมน์ของตารางเด็ดขาด เพราะโมเดลจะอ่านข้อมูลจากคอลัมน์ที่ 1 ข้ามไปคอลัมน์ที่ 2 ในบรรทัดเดียวกัน ซึ่งผิดหลักการอ่านตาราง

### 5.2 การจัดการรูปภาพสอดแทรกและคำบรรยาย (ImageRegion & Caption)
- หากในเอกสารมีรูปวาด ภาพถ่าย หรือลวดลายประดับ ต้องตีวง Polygon ล้อมรอบและกำหนดเป็น `<ImageRegion>`
- ห้ามนำรูปภาพไปปะปนกับ TextRegion เด็ดขาด โมเดล HTR ไม่สามารถ "อ่าน" ลวดลายรูปภาพได้ มันจะสับสน
- หากรูปภาพมีคำบรรยายใต้ภาพ (Caption) ให้แยกคำบรรยายนั้นสร้างเป็น TextRegion ชนิด caption

### 5.3 การจัดการเชิงอรรถ (Footnotes)
- เชิงอรรถควรถูกจัดกลุ่มเป็น TextRegion แยกต่างหาก และกำหนดคุณสมบัติให้เป็นเชิงอรรถ
- การจัดการ Reading Order: เชิงอรรถควรถูกกำหนดให้อ่านหลังสุดในหน้านั้นๆ เสมอ (แม้ว่าจะอยู่ตรงกลางหน้าก็ตาม)
- Baseline ของเชิงอรรถมักจะมีขนาดเล็กกว่าปกติ ต้องระมัดระวังในการวาดให้แม่นยำ

### 5.4 การจัดการข้อความริมขอบ (Marginalia)
- ในเอกสารโบราณ มักมีผู้ใช้อ่านบันทึกข้อความริมขอบ (Marginalia)
- ข้อความเหล่านี้มักเขียนในแนวตั้ง เอียง หรืออยู่นอกพื้นที่ทำงานหลัก
- ต้องสร้าง TextRegion ชนิด marginalia และวาด Baseline ตามทิศทางที่ข้อความนั้นถูกเขียน (เช่น หากเขียนแนวตั้ง ก็ต้องลาก Baseline แนวตั้ง)
- ใช้หลักการถอดความ Diplomatic Transcription ตามปกติ

### 5.5 การจัดการตัวอักษรนำขนาดใหญ่ (Drop Capitals)
- ตัวอักษรตัวแรกของย่อหน้าที่ถูกทำให้มีขนาดใหญ่พิเศษ (Drop Capital)
- อาจลาก Baseline ทะลุ Drop Capital ไปโดยรักษาระดับให้ตรงกับตัวอักษรปกติในบรรทัดนั้น
- หรือวาด TextRegion แยกเฉพาะ แล้วใช้ระบบเชื่อมโยงของโครงสร้าง XML ในการต่อคำ

## 6. ตัวอย่างคู่มือจากโปรเจกต์ระดับโลก

การกำหนดแนวปฏิบัติ Ground Truth นี้ถูกใช้งานและพิสูจน์แล้วจากโครงการระดับโลกและเครื่องมือที่ได้รับความนิยมสูงสุดในแวดวง Digital Humanities เครื่องมือที่นิยมประกอบด้วย: [3]

### 6.1 แนวทางจาก eScriptorium
eScriptorium เป็นแพลตฟอร์ม Open-source ที่พัฒนาขึ้นเพื่อใช้งานร่วมกับโมเดล Kraken ซึ่งมีจุดเด่นเรื่อง Baseline-based HTR อย่างชัดเจน
- **ข้อเสนอแนะ:** คู่มือของ eScriptorium เน้นย้ำเรื่องความสำคัญของการวาด Baseline ให้เป็นเส้นตรงใต้ Base character มากที่สุด
- **รูปแบบ:** สนับสนุนโครงสร้าง PAGE XML อย่างเต็มรูปแบบ และบังคับใช้การวาด Polygon ที่ยืดหยุ่น

### 6.2 แนวทางจาก Transkribus
Transkribus เป็นแพลตฟอร์มที่เป็นมาตรฐานอุตสาหกรรมสำหรับการวิจัยด้านประวัติศาสตร์
- **ข้อเสนอแนะ:** แม้ระบบเก่าของ Transkribus จะเคยใช้ Bounding Box แต่แนวทางปฏิบัติปัจจุบันผลักดันให้ใช้ Polygon อย่างเคร่งครัด โดยเฉพาะเมื่อเจอกับภาษาที่มีอักขระซ้อนทับกัน
- **การถอดความ:** คู่มือของ Transkribus มีเนื้อหาครอบคลุมเรื่อง Diplomatic Transcription อย่างลึกซึ้ง และเตือนให้ผู้ทำข้อมูลระวังการเผลอแก้คำผิดเสมอ

### 6.3 แนวทางจาก Aletheia
Aletheia เป็นซอฟต์แวร์ระดับผู้เชี่ยวชาญ (Expert system) สำหรับ Document Image Analysis สร้างโดย PRImA Research (ผู้คิดค้นมาตรฐาน PAGE XML)
- **ข้อเสนอแนะ:** คู่มือของ Aletheia ให้ความสำคัญกับโครงสร้างของ PAGE XML ทุกแท็ก ทุกชนิดของ Region และสอนวิธีการแยกแยะตาราง รูปภาพ และ Marginalia อย่างละเอียด
- **คุณภาพ:** การทำ Ground Truth ด้วย Aletheia มักจะได้ชุดข้อมูลระดับสูงสุดที่พร้อมตีพิมพ์ในงานวิจัยทางวิชาการ

## 7. ภาคผนวก ก: ดัชนีคำศัพท์เทคนิคสำหรับการทำ Ground Truth

เพื่อให้เกิดความเข้าใจที่ตรงกันในทีมพัฒนาชุดข้อมูล นี่คือดัชนีคำศัพท์ที่จำเป็น:
- **Annotation:** การสร้างคำอธิบายหรือกำหนดโครงสร้างลงในรูปภาพเอกสาร
- **Baseline:** เส้นสมมติที่ลากผ่านจุดล่างสุดของตัวอักษรฐาน (Base character) 
- **Bounding Box:** กล่องสี่เหลี่ยมผืนผ้าที่ครอบคลุมข้อความ ใช้แกน X, Y, Width, Height
- **Character Error Rate (CER):** มาตรวัดความผิดพลาดระดับตัวอักษร ยิ่งต่ำยิ่งดี
- **Diplomatic Transcription:** การถอดความแบบรักษาสภาพดั้งเดิมของตัวอักษรและอักขรวิธีให้มากที่สุด
- **Document Layout Analysis (DLA):** กระบวนการวิเคราะห์โครงสร้างหน้ากระดาษ (เช่น แยกรูปภาพ, ตาราง, และข้อความ)
- **Garbage In, Garbage Out:** หลักการที่ว่า หากป้อนข้อมูลสอนที่ผิดพลาดให้ AI ผลลัพธ์ที่ได้ก็จะผิดพลาดตาม
- **Ground Truth (GT):** ข้อมูลที่มีความถูกต้องแม่นยำสูงที่สุด ใช้สำหรับสอนและประเมินผล AI
- **Handwritten Text Recognition (HTR):** การรู้จำอักษรตัวเขียนด้วยปัญญาประดิษฐ์
- **Optical Character Recognition (OCR):** การรู้จำอักษรสำหรับเอกสารตีพิมพ์
- **Overfitting:** การที่โมเดลจดจำข้อมูลสอนได้ดีมาก แต่ไม่สามารถทำนายข้อมูลใหม่ได้
- **Polygon:** รูปหลายเหลี่ยมที่ใช้กำหนดพื้นที่ของข้อความ มีความยืดหยุ่นสูงกว่า Bounding Box
- **Reading Order:** ลำดับการอ่านข้อความในเอกสารจากต้นจนจบ
- **Training Data:** ชุดข้อมูลจำนวนมากที่ใช้สอนโมเดล AI
- **Word Error Rate (WER):** มาตรวัดความผิดพลาดระดับคำ ยิ่งต่ำยิ่งดี
- **Word Segmentation:** กระบวนการแยกข้อความออกเป็นคำๆ

## 8. ภาคผนวก ข: การตรวจสอบคุณภาพข้อมูล (Quality Assurance)

ก่อนที่ข้อมูล Ground Truth จะถูกส่งไปให้โมเดล AI เรียนรู้ จะต้องผ่านขั้นตอน Quality Assurance (QA) อย่างเข้มงวด:
1. **การตรวจสอบโดยมนุษย์ (Human Review):** ทีมงาน QA จะต้องสุ่มตรวจข้อมูลอย่างน้อย 10-20% จากหน้าเอกสารทั้งหมด เพื่อหาข้อผิดพลาดในการวาด Baseline หรือการถอดความ
2. **การตรวจสอบด้วยสคริปต์ (Automated Script Validation):** ใช้โปรแกรมตรวจสอบว่าโครงสร้าง PAGE XML ถูกต้องตาม Schema หรือไม่ และตรวจสอบว่ามีการใช้เครื่องหมายหรืออักขระแปลกปลอมที่อยู่นอกเหนือพจนานุกรมหรือไม่
3. **การวัดอัตราข้อตกลงร่วมกันของผู้จัดทำ (Inter-annotator Agreement):** หากมีผู้ทำ Ground Truth หลายคน ให้ทดลองทำหน้าเดียวกัน แล้วนำผลลัพธ์มาเปรียบเทียบกัน หากตรงกันมากกว่า 95% ถือว่าคู่มือการทำ Ground Truth นั้นชัดเจนพอ
4. **กระบวนการ Feedback Loop:** หากพบข้อผิดพลาด ต้องแจ้งกลับไปยังทีมงานทันทีเพื่อแก้ไขและป้องกันการเกิดซ้ำ

### โค้ดคอมพิวเตอร์คำนวณอัตราความผิดพลาด (CER/WER Calculator)
```python
import numpy as np

def edit_distance(ref: list, hyp: list) -> int:
    n, m = len(ref), len(hyp)
    dp = np.zeros((n + 1, m + 1), dtype=int)
    for i in range(n + 1):
        dp[i][0] = i
    for j in range(m + 1):
        dp[0][j] = j
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            if ref[i - 1] == hyp[j - 1]:
                dp[i][j] = dp[i - 1][j - 1]
            else:
                dp[i][j] = min(dp[i - 1][j] + 1, dp[i][j - 1] + 1, dp[i - 1][j - 1] + 1)
    return dp[n][m]

def calculate_cer(ref: str, hyp: str) -> float:
    ref_chars = list(ref)
    hyp_chars = list(hyp)
    dist = edit_distance(ref_chars, hyp_chars)
    return float(dist) / len(ref_chars) if len(ref_chars) > 0 else 0.0

def calculate_wer(ref: str, hyp: str) -> float:
    ref_words = ref.split()
    hyp_words = hyp.split()
    dist = edit_distance(ref_words, hyp_words)
    return float(dist) / len(ref_words) if len(ref_words) > 0 else 0.0
```

### โค้ดคอมพิวเตอร์คำนวณอัตราความผิดพลาด (CER/WER Calculator)
```python
import numpy as np

def edit_distance(ref: list, hyp: list) -> int:
    n, m = len(ref), len(hyp)
    dp = np.zeros((n + 1, m + 1), dtype=int)
    for i in range(n + 1):
        dp[i][0] = i
    for j in range(m + 1):
        dp[0][j] = j
    for i in range(1, n + 1):
        for j in range(1, m + 1):
            if ref[i - 1] == hyp[j - 1]:
                dp[i][j] = dp[i - 1][j - 1]
            else:
                dp[i][j] = min(dp[i - 1][j] + 1, dp[i][j - 1] + 1, dp[i - 1][j - 1] + 1)
    return dp[n][m]

def calculate_cer(ref: str, hyp: str) -> float:
    ref_chars = list(ref)
    hyp_chars = list(hyp)
    dist = edit_distance(ref_chars, hyp_chars)
    return float(dist) / len(ref_chars) if len(ref_chars) > 0 else 0.0

def calculate_wer(ref: str, hyp: str) -> float:
    ref_words = ref.split()
    hyp_words = hyp.split()
    dist = edit_distance(ref_words, hyp_words)
    return float(dist) / len(ref_words) if len(ref_words) > 0 else 0.0
```

## ภาคผนวก ฎ: คู่มือการควบคุมคุณภาพ: การคำนวณและประเมินค่า CER (Character Error Rate) และ WER (Word Error Rate)
ในการประเมินประสิทธิภาพของระบบรู้จำอักษรเขียนมือ (HTR) ดัชนีวัดเชิงวิเคราะห์ที่มีผลสำคัญที่สุดคืออัตราความผิดพลาดระดับอักขระ (Character Error Rate) และอัตราความผิดพลาดระดับคำ (Word Error Rate) โดยใช้แนวคิดทางคณิตศาสตร์จากระยะห่างแก้ไขของเลเวนชเทน (Levenshtein Distance)

### สูตรคำนวณและวิธีการจัดเตรียมเอกสารประเมินผล
สูตรคำนวณตัวชี้วัดประสิทธิภาพเขียนได้ดังนี้:
$$\text{CER} = \frac{S + I + D}{N}$$
โดยที่:
- $S$ คือจำนวนอักขระที่ต้องการทดแทน (Substitutions)
- $I$ คือจำนวนอักขระที่เพิ่มเข้ามาจากข้อความจริง (Insertions)
- $D$ คือจำนวนอักขระที่ตกหล่นสูญหาย (Deletions)
- $N$ คือจำนวนอักขระทั้งหมดในชุดอ้างอิงอุดมคติ (Ground Truth)

การเก็บข้อมูลเพื่อนำมาเปรียบเทียบในระบบวิชาการมักจะทำโดยการนำเข้าคู่ไฟล์ PAGE XML สองเวอร์ชัน เวอร์ชันอ้างอิง (Reference) และเวอร์ชันผลลัพธ์จากซอฟต์แวร์ HTR (Hypothesis) แล้วดึงข้อความจากแท็ก `<Unicode>` ออกมาเปรียบเทียบความสัมพันธ์ของตัวหนังสือจริงทีละบรรทัด
