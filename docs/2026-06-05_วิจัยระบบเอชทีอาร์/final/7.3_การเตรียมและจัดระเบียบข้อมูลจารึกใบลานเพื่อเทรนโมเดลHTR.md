# บทที่ 7.3: การเตรียมและจัดระเบียบข้อมูลจารึกใบลานเพื่อเทรนโมเดล HTR

คลังข้อมูลสำหรับงานวิจัยระบบคอมพิวเตอร์ถือเป็นรากฐานที่กำหนดระดับสติปัญญาและความแม่นยำของแบบจำลองการเรียนรู้เชิงลึก (Deep Learning Models) สำหรับระบบการรู้จำข้อความใบลานและเอกสารโบราณอักษรขอมไทยและอักษรธรรมล้านนา ความเชื่อถือได้ของตัวทำนาย AI ขึ้นอยู่กับคุณภาพและความครบถ้วนของข้อมูลภาพคู่ข้อความปริวรรตดิบ (Image-Text Pairs) หรือชุดข้อมูล **Ground Truth** ที่ป้อนเข้าสู่กระบวนการเรียนรู้ การจัดการข้อมูลสะเปะสะปะหรือข้อความถอดคำสะกดที่มีการคลาดเคลื่อนจะเหนี่ยวรังให้เกิดภาวะ "ขยะเข้าขยะออก" (Garbage In, Garbage Out) ซึ่งจำกัดประสิทธิภาพของโมเดล [1] บทนี้จะนำเสนอแนวปฏิบัติและกลวิธีเชิงลึกในการบริหาร จัดเก็บ จัดระเบียบ และการแปรรูปข้อมูลจารึกใบลานเพื่อจัดทำชุดข้อมูลสอนที่มั่นคงและสอดคล้องกับมาตรฐานทางวิศวกรรมข้อมูลระดับสากล

## 7.3.1 การตรวจสอบคุณภาพและการคัดกรองรูปภาพใบลานดิบ (Image Curation)

ขั้นตอนแรกของการจัดเก็บชุดข้อมูลคือ การคัดเลือกและทำความสะอาดภาพถ่ายต้นฉบับดิจิทัลของคัมภีร์ใบลานและสมุดข่อย ซึ่งมีเกณฑ์การประเมินคุณภาพใน 3 มิติหลักดังนี้:

### 1. เกณฑ์การคัดกรองความคมชัดและลายเส้นอักษร (Clarity & Contrast Criteria)
ภาพถ่ายใบลานที่เลือกใช้ต้องมีความละเอียดเชิงพื้นที่เพียงพอในการแสดงรายละเอียดขอบอักษรและวรรณยุกต์ซ้อนตัวล่าง โดยมีข้อกำหนดทางเทคนิคในการประเมินเบื้องต้นคือ:
- **ความละเอียดขั้นต่ำ:** ภาพที่ถ่ายควรมีค่าความหนาแน่นพิกเซลไม่น้อยกว่า 300 DPI (Dots Per Inch) เพื่อรักษารูปร่างย่อย (Features) ของอักขระตัวเชิง
- **ความเปรียบต่างเชิงแสง (Contrast):** ภาพถ่ายต้องได้รับการจัดแสงแบบสาดเฉียง (Raking Light) ปราศจากแสงสะท้อนจ้า (Glare) หรือเงาตึกทับซ้อนบดบังอักษร หากพบภาพที่มีปัญหาแสงและเงาไม่สม่ำเสมอ หรือความเปรียบต่างระหว่างรอยจารกับพื้นใบลานมีน้อยเกินไป ภาพดังกล่าวจะต้องส่งผ่านระบบประมวลผลขั้นต้นด้วยสคริปต์กรอง Sauvola Binarization ตามที่ระบุไว้ในคู่มือบทที่ 3.2
  - **การปรับแต่ง Sauvola:** ในวิศวกรรมคอมพิวเตอร์วิทัศน์ พารามิเตอร์ของ Sauvola เช่น ขนาดหน้าต่างกวาดสัญญาณ (Window Size: $w$) และค่าสัมประสิทธิ์การเบี่ยงเบนมาตรฐาน (Threshold Parameter: $k$) ต้องได้รับจูนอย่างระมัดระวัง สำหรับอักษรโบราณ แนะนำให้ตั้งค่า $w = 25$ และ $k = 0.2$ ถึง $0.3$ เพื่อรักษาเส้นแกนพยัญชนะโบราณไม่ให้ขาดวิ่นหรือหลอมรวมกันเป็นก้อนสีดำ

### 2. การควบคุมความสม่ำเสมอของลักษณะตัวเขียน (Script Consistency)
ในคัมภีร์ใบลานชุดเดียวกันอาจบันทึกโดยนักจารต่างคนต่างช่วงเวลากัน การผสมผสานลายมือเขียนที่มีลักษณะต่างกันอย่างสุดขั้วลงในชุดข้อมูลขนาดเล็ก จะทำให้แบบจำลองลูปประมวลผลสับสนและลดความแม่นยำในการรู้จำคำ ดังนั้น นักวิจัยจึงควรจัดแบ่งประเภทของลายมือจารออกเป็นกลุ่มๆ (Linguistic Clusters) เช่น ลายมือตัวบรรจงระเบียบอารามหลวง ลายมือตัวหวัดปานกลางสำหรับคำสอนทั่วไป และลายมือตัวเขียนตามบ้านเรือน เพื่อแยกเทรนโมเดลเฉพาะหรือเพื่อผสมข้อมูลในอัตราส่วนที่ควบคุมได้ [2]

### 3. การคัดทิ้งภาพชำรุดเสียหายเกินเยียวยา
ในกรณีที่พบใบลานมีรอยผุกร่อน ขอบหัก หรือเศษใบไม้ลานฉีกขาดจนลบล้างข้อความไปมากกว่า 50% ของเส้นบรรทัด ภาพเหล่านั้นควรถูกคัดแยกออกจากฐานข้อมูลฝึกสอนทั่วไป เนื่องจากไม่สามารถสร้างข้อความ Ground Truth ที่ถูกต้องได้ แต่สามารถนำไปใช้ในขั้นตอนทดสอบความทนทานต่อสัญญาณรบกวนของโมเดลในภายหลัง

## 7.3.2 โครงสร้างโฟลเดอร์และการตั้งชื่อระบบไฟล์ตามมาตรฐาน (Metadata & File Naming)

การรักษาความเป็นระเบียบเรียบร้อยของการจัดเก็บชุดข้อมูลช่วยให้การดึงไฟล์ไปประมวลผลและการสืบค้นย้อนกลับ (Traceability) ดำเนินไปอย่างสะดวก โครงการจึงกำหนดมาตรฐานโครงสร้างไดเรกทอรีและสัญนิยมการตั้งชื่อไฟล์สากลดังนี้:

### 1. โครงสร้างโฟลเดอร์ในสภาพแวดล้อมใช้งานจริง
ชุดข้อมูล Ground Truth จะจัดระบบแยกจากซอร์สโค้ดและไลบรารีอย่างเด็ดขาด โดยแสดงตัวอย่างลำดับชั้นโฟลเดอร์ดังต่อไปนี้:
```
dataset_root/
├── metadata.json
├── train/
│   ├── images/
│   │   ├── LANNA_001_L01.png
│   │   └── LANNA_001_L02.png
│   └── pagexml/
│       ├── LANNA_001_L01.xml
│       └── LANNA_001_L02.xml
├── val/
│   ├── images/
│   └── pagexml/
└── test/
    ├── images/
    └── pagexml/
```

### 2. สัญนิยมการตั้งชื่อไฟล์ (File Naming Conventions)
ชื่อไฟล์ภาพและไฟล์คำกำกับ (Annotation/XML Files) ต้องเป็นสากลและไม่ใช้ภาษาไทยหรือตัวอักษรพิเศษเพื่อหลีกเลี่ยงข้อผิดพลาดเชิงระบบปฏิบัติการ (OS Path Encoding Errors) รูปแบบโครงสร้างตั้งชื่อคือ:
```
[SCRIPT_TYPE]_[MANUSCRIPT_ID]_[LINE_ID].[EXTENSION]
```
- **SCRIPT_TYPE:** ประเภทอักษร เช่น `KHOM` สำหรับอักษรขอมไทย, `LANNA` สำหรับอักษรธรรมล้านนา
- **MANUSCRIPT_ID:** รหัสระบุคัมภีร์ใบลานหรือผูกใบลานแบบ 3 หลัก เช่น `001`
- **LINE_ID:** รหัสระบุลำดับหน้าและเส้นบรรทัด เช่น `F02L01` (หน้า 2 ด้านหน้า เส้นบรรทัดที่ 1)
- **ตัวอย่างชื่อไฟล์สมบูรณ์:** `KHOM_105_F03L02.png` คู่กับ `KHOM_105_F03L02.xml` [3]

### 3. ตัวอย่างการออกแบบสคีมาเมทาดาตา (Metadata Schema Example)
ในการเก็บบันทึกประวัติและบริบทของคัมภีร์ใบลาน ควรมีไฟล์ `metadata.json` จัดเก็บเพื่อประโยชน์ทางมานุษยวิทยาและวิศวกรรมข้อมูล ตัวอย่างโครงสร้างข้อมูลคือ:
```json
{
  "manuscript_id": "LANNA_001",
  "title_th": "มังรายศาสตร์ฉบับวัดเสาหิน",
  "script_type": "Tai Tham",
  "language": "Northern Thai",
  "material": "Palm leaf",
  "origin_location": "วัดเสาหิน เชียงใหม่",
  "estimated_date": "พ.ศ. 2380",
  "total_pages": 48,
  "annotator_ids": ["ANN_01", "ANN_02"],
  "license": "CC-BY-NC-SA-4.0"
}
```

## 7.3.3 แนวทางและมาตรการการปริวรรตข้อความเฉลย (Ground Truth Standards)

หัวใจสำคัญของการสร้างชุดข้อมูล HTR อยู่ที่ระดับความสมบูรณ์ในการถอดความสะกดของนักอักษรศาสตร์โบราณ โดยโครงการได้กำหนดแนวทางและกระบวนการควบคุมคุณภาพข้อมูลไว้ดังนี้:

### 1. สัจนิยมอักขรวิธีสะกดตามจริง (Diplomatic Transcription)
การปริวรรตข้อความเพื่อใช้สอนแบบจำลองปัญญาประดิษฐ์ต้องสะกดตรงตามรูปลักษณ์พิกเซลที่ปรากฏบนคัมภีร์ใบลานจริงโดยห้ามแก้ไขคำสะกดผิดหรือปรับเปลี่ยนพยัญชนะให้เป็นภาษาปัจจุบัน (Diplomatic Transcription) ตัวอย่างเช่น:
- หากพบคัมภีร์จารผิดคำว่า *พุทธ* เป็น *พุธ* นักปริวรรตต้องพิมพ์สะกดเป็น *พุธ* ตามรูปเขียน ห้ามปรับเป็นรูปแก้ไขประวัติศาสตร์ เนื่องจากโมเดล HTR เรียนรู้ความสัมพันธ์เชิงภาพพิกเซล หากรูปพิมพ์ไม่ตรงกับรูปภาพ ภาพตัวอักษรของ AI จะเกิดการเรียนรู้คลาดเคลื่อนและส่งผลลบล้างต่อความแม่นยำโดยรวม [4]

### 2. ขบวนการตรวจทานสองทาง (Double-Blind Verification)
เพื่อหลีกเลี่ยงข้อผิดพลาดส่วนบุคคลของนักจารและนักถอดข้อความ โครงการกำหนดให้ใช้ระบบ **Double-Blind Keying** โดยมอบหมายให้นักอักษรศาสตร์ 2 ท่านทำการปริวรรตข้อความจากภาพถ่ายเดียวกันอย่างอิสระ จากนั้นใช้โปรแกรมประเมินความสอดคล้องระหว่างคำสะกดด้วยดัชนีวัดความคล้าย เช่น อัตราความคลาดเคลื่อนระดับตัวอักษร (Grapheme-level Difference) หากพบจุดที่มีความคลาดเคลื่อน (Discrepancy) ข้อความคู่ขนานจะถูกส่งไปประเมินและตัดสินคำสะกดสุดท้ายโดยผู้เชี่ยวชาญอาวุโส (Adjudicator) เพื่อชำระข้อผิดพลาดให้เหลือศูนย์ [5] การใช้วิธีนี้ช่วยเพิ่มประสิทธิภาพในการคงคุณภาพ Ground Truth ได้สูงกว่า 99%

## 7.3.4 ยุทธวิธีการจัดแบ่งชุดข้อมูลเพื่อหลีกเลี่ยงการรั่วไหล (Data Partitioning)

การแบ่งชุดข้อมูลออกเป็นชุดฝึกสอน (Train Set) ชุดตรวจสอบสภาวะการเรียนรู้ (Validation Set) และชุดทดสอบสุดท้าย (Test Set) ต้องดำเนินไปอย่างระมัดระวังเพื่อความเที่ยงตรงทางสถิติและป้องกันข้อผิดพลาดเชิงระบบ:

### 1. สัดส่วนการแบ่งเป้าหมาย (Data Splitting Ratio)
- **Train Set (70%):** ใช้สำหรับฝึกสอนและปรับน้ำหนักพารามิเตอร์ของแบบจำลองประสาท
- **Validation Set (15%):** ใช้ตรวจวัดค่าสูญเสียในระหว่างการประเมินรอบการเรียนรู้เพื่อตัดสินใจปรับอัตราการสุ่มปิดโครงข่าย (Dropout) และการเลือกจังหวะเวลายุติเทรน (Early Stopping)
- **Test Set (15%):** ชุดข้อมูลเป้าหมายสุดท้ายที่ไม่เคยผ่านระบบการเทรนมาก่อน ใช้สำหรับสรุปผลรายงานค่า CER และ WER ขั้นสุดท้ายของโครงการ [6]

### 2. การป้องกันข้อมูลรั่วไหลระดับเอกสาร (Document-level Leakage Prevention)
ข้อผิดพลาดทางวิศวกรรมข้อมูลที่พบบ่อยในการพัฒนา HTR คือ การสุ่มแบ่งบรรทัดภาพถ่ายจากคัมภีร์เล่มเดียวกันกระจายลงในทั้ง Train และ Test Set ซึ่งส่งผลให้แบบจำลอง HTR คุ้นเคยและจดจำรูปแบบลายมือเขียนเฉพาะตัวของอาลักษณ์จารเล่มนั้นๆ ทำให้ผลประเมินตัวเลข CER ของชุดทดสอบดีเกินจริง (Overfitting to Specific Handwriting) แต่เมื่อนำโมเดลไปใช้งานกับคัมภีร์ใบลานเล่มใหม่ของวัดอื่น โมเดลจะกลับทำงานล้มเหลว
- **วิธีแก้ไขในเชิงยุทธศาสตร์:** การจัดสรรต้องใช้วิธี **Document-level / Manuscript-level Splitting** คือ ภาพแถบบรรทัดทั้งหมดที่ตัดแบ่งจากคัมภีร์เล่มที่ 1 จะต้องถูกจัดให้อยู่ในกลุ่ม Train Set เท่านั้น ในขณะที่คัมภีร์เล่มที่ 2 ซึ่งเขียนด้วยลายมืออื่นจะถูกจัดสรรแยกให้อยู่ใน Test Set ทั้งเล่ม เพื่อให้การวัดผลทดสอบสะท้อนความสามารถในการอ่านอักษรลายมือแปลกใหม่ (Generalization Capability) ของระบบ AI อย่างถูกต้อง [7]

สำหรับโครงการที่มีขนาดข้อมูลเล็กมาก (Low-Resource Context) โครงการอาจจะเลือกใช้ระบบการตรวจสอบข้ามแบบ K-พับ (K-fold Cross Validation) ในระดับคัมภีร์ เพื่อประเมินค่าเสถียรภาพรวมของแบบจำลองคอมพิวเตอร์อย่างเป็นกลาง

## 7.3.5 ขบวนการแปรรูปและแปลงสกัดชุดข้อมูลเชิงข้อมูลวิศวกรรม (Data Compilation)

ก่อนส่งข้อมูลเข้าสู่เครื่องยนต์ Kraken CLI ภาพบรรทัดและไฟล์พิกัด PAGE XML จะต้องถูกแปลงรวบรวมข้อมูลให้เป็นรูปแบบที่สามารถประมวลผลได้อย่างรวดเร็วผ่านทางอินเทอร์เฟซคอมพิวเตอร์:

### 1. การแปลงขนาดและความละเอียดภาพบรรทัด (Resolution Standardization)
แถบรูปภาพที่ตัดแบ่งตามเส้นฐานบิดโค้งจะมีความกว้างไม่แน่นอน โครงสร้างข้อมูลระบบจะต้องสเกลภาพให้มีความสูงคงที่เท่ากับ **120 พิกเซล** เป็นมาตรฐานหลักตามที่วิเคราะห์ไว้ในบทเรียนเทคนิค บทที่ 6.2 เพื่อคงคุณภาพรายละเอียดอักษรซ้อนเชิงล้านนา โดยมีสคริปต์คอมพิวเตอร์รองรับการแปลงและคงอัตราส่วนรูปภาพ (Aspect Ratio) เพื่อป้องกันภาพยืดหรือบดบี้

### 2. การสร้างไฟล์รวบรวมฐานข้อมูลสากล (Arrow compilation)
เอนจินของ Kraken ทำการอ่านไฟล์ชุดข้อมูลภาพปริวรรตแบบรวมศูนย์ผ่านโครงสร้างไบนารีไฟล์นามสกุล **.arrow** ซึ่งนักวิจัยสามารถประมวลผลแปรรูปภาพและไฟล์ PAGE XML ได้โดยรันคำสั่งคอมไพล์เดโมดังนี้:
```bash
# คำสั่งการคอมไพล์ข้อมูลรูปภาพและ PAGE XML เป็นชุดข้อมูล Arrow ใน Kraken
ketos compile -f page -o D:/01_APP/HTR_Research/compiled_data/train.arrow D:/01_APP/HTR_Research/raw_data/train/*.xml
```
*หมายเหตุ:* ข้อมูลที่ผ่านการคอมไพล์เป็นไฟล์เดี่ยว `.arrow` จะเพิ่มประสิทธิภาพในการอ่านข้อมูลเข้าสู่หน่วยความจำของกราฟิกการ์ด GPU ระหว่างช่วงเวลาฝึกสอนโมเดลขึ้นอย่างชัดเจนเมื่อเทียบกับการดึงไฟล์ภาพย่อยหลักหมื่นรูปโดยตรงจากฮาร์ดดิสก์ [8] การจัดเตรียมคอมไพล์นี้ยังรองรับการแบ่งชุดข้อมูลย่อย (Mini-batches) ในสัญนิยมการเรียนรู้แบบสุ่ม (Stochastic Gradient Descent) ได้อย่างรวดเร็ว

## สรุป

การจัดเตรียมและทำความสะอาดข้อมูลจารึกใบลานเป็นหัวใจของการเอาชนะข้อจำกัดระบบ HTR อักษรขอมไทยและอักษรธรรมล้านนา มาตรฐานการคัดเลือกภาพใบลานที่มีความเปรียบต่างสูง การจัดโครงสร้างไดเรกทอรีที่เป็นเอกภาพ การปริวรรตสะกดตามจริงตามรูปเขียน (Diplomatic Transcription) ตลอดจนการป้องกันการรั่วไหลของข้อมูลลายมือผ่านแนวคิด Document-level Splitting ล้วนเป็นเงื่อนไขจำเป็นทางวิศวกรรมที่จะส่งเสริมให้โมเดลมีค่า CER ต่ำกว่า 3% การรักษามาตรฐานข้อมูลที่ดีในชั้นเตรียมการนี้จะนำไปสู่อัตราการเรียนรู้ที่รวดเร็วและการลดโอกาสโมเดลเรียนรู้ทับซ้อนที่จำกัดวงในระหว่างการจัดทำโมเดลเพิ่มความหลากหลายของลายมือ ซึ่งจะอภิปรายอย่างละเอียดในบทถัดไป (บทที่ 7.4)
