# 10 การจัดการภาษาไทยและ Non-Latin ใน XML

> เอกสารฉบับนี้อธิบายถึงความท้าทาย แนวทางแก้ไข และแนวปฏิบัติ (Best Practices) ในการจัดเก็บข้อมูลโครงสร้างข้อความภาษาไทยและภาษาในกลุ่ม Non-Latin (เช่น ภาษาอาหรับ, เทวนาครี) ลงในมาตรฐาน XML (เช่น ALTO และ PAGE XML) สำหรับงานวิจัยด้าน Digital Humanities และระบบ Optical Character Recognition (OCR) / Handwritten Text Recognition (HTR) เอกสารนี้ครอบคลุมตั้งแต่ระดับโครงสร้างอักขระ ปัญหาพิกัดภาพ ไปจนถึงแนวทางการจัดทำข้อมูลสอน (Ground Truth) ที่ถูกต้อง

## 1. ความซับซ้อนของภาษาไทยในการทำ Digitalization (4 ระดับอักษร, ไม่มีช่องว่าง)

การนำเข้าเอกสารภาษาไทยเข้าสู่กระบวนการ Digitalization เพื่อสร้างข้อความแบบฉบับดิจิทัล (Digital Text) ผ่านกระบวนการ OCR (Optical Character Recognition) หรือ HTR (Handwritten Text Recognition) มีความซับซ้อนและท้าทายกว่าภาษาในกลุ่มละติน (Latin scripts) อย่างภาษาอังกฤษเป็นอย่างมาก ทั้งนี้ไม่ได้เป็นเพียงปัญหาด้านอัลกอริทึม แต่เป็นข้อจำกัดเชิงโครงสร้างของตัวอักษรเอง

### 1.1 โครงสร้างอักษร 4 ระดับ (4-Level Character Structure)

ภาษาไทยเป็นภาษาที่มีการวางตำแหน่งของตัวอักษร สระ และวรรณยุกต์ ซ้อนกันในแนวดิ่ง (Stacking vowels/tone marks) อย่างเป็นระบบ ซึ่งต่างจากภาษาละตินที่เรียงต่อกันในแนวนอน (Linear sequence) อย่างเดียว โครงสร้าง 4 ระดับนี้สามารถอธิบายได้ดังนี้:

1. **ระดับเหนือวรรณยุกต์ (Above Tone Mark Level)**: ระดับบนสุด มักเป็นที่อยู่ของวรรณยุกต์ (เช่น ่, ้, ๊, ๋) หรือเครื่องหมายพิเศษ (เช่น ทัณฑฆาต ์) เครื่องหมายเหล่านี้จะอยู่เหนือสระบน หรือเหนือพยัญชนะหลักโดยตรง
2. **ระดับสระบน (Upper Vowel Level)**: ระดับเหนือพยัญชนะหลัก เป็นที่อยู่ของสระบน (เช่น ิ, ี, ึ, ื) และไม้หันอากาศ (ั) หรือไม้ไต่คู้ (็) 
3. **ระดับพยัญชนะหลัก (Base Character Level)**: ระดับกลาง เป็นที่อยู่ของพยัญชนะ ก-ฮ รวมถึงสระบางตัวที่อยู่ในระดับเดียวกับพยัญชนะ (เช่น เ, แ, โ, ใ, ไ, ะ, า) นี่คือระดับแกนกลางที่กำหนดเส้น Baseline
4. **ระดับสระล่าง (Lower Vowel Level)**: ระดับใต้พยัญชนะหลัก เป็นที่อยู่ของสระล่าง (เช่น ุ, ู) และพินทุ (ฺ)

**ตารางที่ 1.1: ตัวอย่างการวิเคราะห์คำตามระดับอักษร 4 ระดับโดยละเอียด**

| คำศัพท์ต้นฉบับ | เหนือวรรณยุกต์ (Level 1) | สระบน (Level 2) | พยัญชนะหลัก (Level 3) | สระล่าง (Level 4) | การจัดเรียงในหน่วยความจำ (Memory Layout) |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **กา** | - | - | ก, า | - | `ก (U+0E01)`, `า (U+0E32)` |
| **ปู** | - | - | ป | ู | `ป (U+0E1B)`, `ู (U+0E39)` |
| **ที่** | ่ (ไม้เอก) | ี (สระอี) | ท | - | `ท (U+0E17)`, `ี (U+0E35)`, `่ (U+0E48)` |
| **ผู้** | ้ (ไม้โท) | - | ผ | ู | `ผ (U+0E1C)`, `ู (U+0E39)`, `้ (U+0E49)` |
| **พันธุ์** | ์ (การันต์) | ุ (สระอุ) | พ, น, ธ | - | `พ (U+0E1E)`, `ั (U+0E31)`, `น (U+0E19)`, `ธ (U+0E18)`, `ุ (U+0E38)`, `์ (U+0E4C)` |
| **น้ำ** | ้ (ไม้โท) | ำ (สระอำ) | น | - | `น (U+0E19)`, `้ (U+0E49)`, `ำ (U+0E33)` |

โครงสร้าง 4 ระดับนี้ ทำให้ขนาดความสูงของแต่ละบรรทัด (Line height) ในเอกสารภาษาไทยมีความแปรปรวน (Variable) อย่างมาก ขึ้นอยู่กับว่าคำในประโยคนั้นมีส่วนประกอบในระดับที่ 1 และ 4 มากน้อยเพียงใด

### 1.2 การเปรียบเทียบกับภาษาละติน (Latin Scripts)

เพื่อให้เห็นภาพความซับซ้อนชัดเจนขึ้น ลองเปรียบเทียบกลไกการวาดพื้นที่ตัวอักษรระหว่างภาษาละตินและภาษาไทย:

**ภาษาละติน (English, French, etc.)**
```text
Ascender line  ->  h  b  d  k  l
Cap height     ->  H  B  D  K  L
Mean line      ->  a  c  e  m  n
Baseline       ->  a  b  c  d  e  (ยึดเป็นฐาน)
Descender line ->  g  p  q  y
```
ในภาษาละติน ตัวอักษรอย่าง 'g' หรือ 'p' จะมีหางย้อยลงมาใต้ Baseline (เรียกว่า Descender) และ 'h' หรือ 'b' จะมีก้านชูขึ้นไป (Ascender) แต่ทั้งหมดเป็น "อักขระเดี่ยว" ไม่ใช่การนำเครื่องหมายหลายชิ้นมาวางซ้อนกันบนพื้นที่พิกัด X เดียวกัน

**ภาษาไทย (Thai)**
ในพื้นที่พิกัด X เดียวกัน (ความกว้างเท่ากับพยัญชนะหนึ่งตัว) อาจมีอักขระซ้อนกันถึง 3 ตัว (เช่น คำว่า "ที่" = ท + ี + ่) สิ่งนี้ทำให้โมเดลคอมพิวเตอร์วิทัศน์ (Computer Vision) รุ่นเก่าที่พยายามแบ่งภาพเป็นคอลัมน์แนวตั้ง (Vertical projection profile) ประสบความล้มเหลวโดยสิ้นเชิง เพราะไม่สามารถหา "ช่องว่าง" ระหว่างตัวอักษรในแนวตั้งได้

### 1.3 ปัญหาความไม่มีช่องว่างระหว่างคำ (No Word Spacing)

ข้อแตกต่างที่สำคัญที่สุดระหว่างภาษาไทยและภาษาอังกฤษ คือภาษาอังกฤษใช้ **"ช่องว่าง (Space)"** เป็นตัวแบ่งคำ (Word boundary) อย่างชัดเจน แต่ภาษาไทยเขียนติดกันเป็นประโยคยาว โดยจะใช้ช่องว่างเพื่อแบ่งวลี หรือประโยค เท่านั้น นี่เป็นลักษณะที่พบได้ในภาษาเอเชียอื่นๆ ด้วย เช่น ภาษาจีน และภาษาญี่ปุ่น (Continuous script)

**ตัวอย่างภาษาอังกฤษ (Space-delimited):**
```text
The quick brown fox jumps over the lazy dog.
(คอมพิวเตอร์สามารถใช้ช่องว่างเพื่อแยกคำได้ทันที: "The", "quick", "brown", "fox")
```

**ตัวอย่างภาษาไทย (No word spacing):**
```text
ตากลมตากลมตากลม
```
ประโยคด้านบนสามารถตีความได้หลายแบบ ขึ้นอยู่กับบริบท:
- ตา-กลม-ตาก-ลม-ตา-กลม (Round eyes dry in the wind round eyes)
- ตาก-ลม-ตา-กลม-ตาก-ลม (Dry in the wind round eyes dry in the wind)

การไม่มีช่องว่างระหว่างคำนี้ ส่งผลต่อระดับ `<Word>` ใน PAGE XML และ ALTO XML อย่างมาก ทำให้ segmentation ระดับคำด้วยวิธีพิจารณาจากพิกัดภาพ (Visual features) เพียงอย่างเดียวทำได้ยาก หรือแทบเป็นไปไม่ได้เลยในบางกรณี ระบบ HTR/OCR จึงมักทำ segmentation และ recognition แค่ระดับบรรทัด `<TextLine>` เท่านั้น แล้วส่งต่อให้โมเดลประมวลผลภาษาธรรมชาติ (NLP) ไปทำ Word Tokenization ในภายหลัง

### 1.4 ผลกระทบต่อกระบวนการทำ Line Segmentation

ผลกระทบเชิงประจักษ์จากลักษณะพิเศษทั้ง 4 ระดับ และการไม่มีช่องว่างระหว่างคำ ทำให้การขีดเส้นแบ่งบรรทัด (Line Segmentation) ในเอกสารโบราณ หรือเอกสารที่มีการพิมพ์เบียดกัน (Tight leading) กลายเป็นฝันร้ายของวิศวกรข้อมูล

เครื่องมือทำ Segmentation อัตโนมัติมักจะตีเส้นตัดผ่านสระ ู ุ ของบรรทัดบน หรือสระ ิ ี ของบรรทัดล่างขาดหายไป ทำให้ข้อมูลที่นำไปสอน AI เสียหายตั้งแต่เริ่มต้น

### 1.5 ตารางอักขระ Unicode และระดับของอักษรภาษาไทย

การจัดกลุ่มรหัส Unicode ตามระดับความสูงมีความสำคัญต่อการเขียน Script ประมวลผลก่อนเข้ากระบวนการวิเคราะห์ XML:

**ตารางที่ 1.2: กลุ่มรหัส Unicode ภาษาไทยและระดับอักษร (Level)**

| ระดับ (Level) | ลักษณะทางกายภาพ | ชุดอักขระตัวอย่าง | ช่วงรหัส Unicode (Hex) |
| :--- | :--- | :--- | :--- |
| Level 1 | เหนือสระบน (Tone Marks) | ่ ้ ๊ ๋ ์ ํ ็ | U+0E47 - U+0E4E |
| Level 2 | สระบน (Upper Vowels) | ิ ี ึ ื ั | U+0E31, U+0E34 - U+0E37 |
| Level 3 | พยัญชนะหลัก (Base Consonants) | ก ข ค ... ฮ | U+0E01 - U+0E2E |
| Level 3 | สระระดับเดียวกับพยัญชนะ (Base Vowels)| เ แ โ ใ ไ ะ า | U+0E30, U+0E32, U+0E40 - U+0E44 |
| Level 4 | สระล่าง (Lower Vowels) | ุ ู ฺ | U+0E38 - U+0E3A |

## 2. ปัญหา Bounding Box ใน ALTO เมื่อเจอสระบน/ล่างซ้อนทับ (พร้อมแผนภาพ/ตารางวิเคราะห์)

มาตรฐาน ALTO XML ถือกำเนิดขึ้นโดยอิงกับการจัดการเอกสารภาษาตะวันตกเป็นหลัก ซึ่งการตีกรอบล้อมรอบตัวอักษรหรือคำ มักใช้รูปทรงสี่เหลี่ยมผืนผ้า หรือ **Bounding Box** เนื่องจากภาษาละตินไม่มีการซ้อนทับกันอย่างซับซ้อนในแนวดิ่ง

### 2.1 โครงสร้างดั้งเดิมของ ALTO XML และ Bounding Box

ในโครงสร้างพื้นฐานของ ALTO XML (เวอร์ชันแรกๆ) จะเก็บข้อมูลพิกัดของ TextLine และ String ในรูปแบบตัวเลข 4 ค่าหลัก ได้แก่:
- `HPOS` (Horizontal Position): พิกัด X ของมุมซ้ายบน
- `VPOS` (Vertical Position): พิกัด Y ของมุมซ้ายบน
- `WIDTH`: ความกว้างของกล่อง (ขยายไปทางขวา)
- `HEIGHT`: ความสูงของกล่อง (ขยายลงด้านล่าง)

```xml
<!-- ตัวอย่าง ALTO XML ของคำว่า "Hello" -->
<String ID="S1" CONTENT="Hello" HPOS="100" VPOS="200" WIDTH="150" HEIGHT="40"/>
```
กล่องที่วาดขึ้นมานี้ จะเป็นรูปทรงสี่เหลี่ยมผืนผ้าตั้งฉากกับแกน X และ Y เสมอ ไม่สามารถเอียง หมุน หรือบิดเบี้ยวได้

### 2.2 ปัญหาการซ้อนทับ (Overlap) ระหว่างบรรทัด

ตามข้อมูล "Verified Data" ข้อที่ 2: ภาษาไทยมีระดับอักษร 4 ระดับ การวาด Bounding Box (ALTO) มักจะทับซ้อนกัน (Overlap) ระหว่างบรรทัด 

เมื่อ Bounding Box ของสองบรรทัดทับซ้อนกัน โมเดล Machine Learning ที่ใช้ข้อมูลพิกัดเหล่านี้ในการฝึกสอน (Training) จะเกิดความสับสน (Confusion) ว่าพิกเซลในบริเวณที่ทับซ้อนกันนั้น (Intersection Area) เป็นของบรรทัดบนหรือบรรทัดล่าง

**ตารางที่ 2.1: วิเคราะห์ความรุนแรงของปัญหาการซ้อนทับ (Overlap) ตามสถานการณ์**

| สถานการณ์ของข้อความ | บรรทัดที่ 1 (บรรทัดบน) | บรรทัดที่ 2 (บรรทัดล่าง) | โอกาสเกิด Overlap | ผลกระทบต่อ Bounding Box (ALTO) |
| :--- | :--- | :--- | :---: | :--- |
| **1. ไม่มีสระยื่นทั้งคู่** | นกบินมาบนฟ้า | คนเดินไปตามทาง | ต่ำมาก | Box แยกกันชัดเจน ไม่เกิดปัญหา |
| **2. บนมีล่าง, ล่างไม่มี** | **ปู่ดูงู**อยู่ในรู | ตามาหาตายาย | ต่ำ | สระ ู ของบรรทัดบน ยื่นลงมา แต่บรรทัดล่างไม่มีสระบน จึงไม่ชนกัน |
| **3. บนไม่มี, ล่างมีบน** | ตามาหาตายาย | **ที่นี่มี**ผีเสื้อ | ต่ำ | วรรณยุกต์บรรทัดล่าง ยื่นขึ้นไป แต่บรรทัดบนไม่มีสระล่าง จึงไม่ชน |
| **4. บนมีล่าง, ล่างมีบน** | **ผู้ใหญ่ดูปู** | **พี่นี่หนีที่**นี่ | **สูงมาก** | สระ ู (บน) ชนกับ ี (ล่าง) Box ทับซ้อนกันชัดเจน ส่งผลร้ายแรง |
| **5. เอกสารโบราณพิมพ์เบียด** | **ผู้ใหญ่ดูปู** | **พี่นี่หนีที่**นี่ | **วิกฤต** | สระชนกันทางกายภาพ (หมึกติดกัน) Box ใช้งานไม่ได้เลย |

### 2.3 แผนภาพจำลองปัญหา Bounding Box ซ้อนทับ

ลองจินตนาการถึงข้อความสองบรรทัดที่มีระยะห่างบรรทัด (Line spacing) แคบ:

บรรทัดที่ 1: `ปู่ดูงู` (มีสระ ู ขยายขอบเขตด้านล่างอย่างมาก)
บรรทัดที่ 2: `ที่นี่มี` (มีสระ ี และวรรณยุกต์ ่ ขยายขอบเขตด้านบนอย่างมาก)

เมื่อวาด Bounding Box แบบ ALTO (สี่เหลี่ยมผืนผ้า) จะเกิดเหตุการณ์ดังแผนภาพนี้:

```text
Bounding Box บรรทัด 1 (ขอบเขตแสดงด้วยเส้น +---+ และ |)
+---------------------------------------+  <- VPOS = 100
|     ่        ่                        |  <- ระดับวรรณยุกต์
|   ปู       ดู       งู                  |  <- ระดับพยัญชนะ
|     ู        ู       ู                  |  <- ระดับสระล่าง
+---|-----------------------------------|  <- ฐาน Box 1 (VPOS + HEIGHT = 180)
    |   พื้นที่ทับซ้อน (Overlap Zone)        |
+---|-----------------------------------|  <- หลังคา Box 2 (VPOS = 160)
|   |  ่       ่                        |  <- ระดับวรรณยุกต์ (ของบรรทัด 2)
|   | ท       น       ม                  |  <- ระดับพยัญชนะ (ของบรรทัด 2)
|   |  ี       ี       ี                  |  <- ระดับสระบน (ของบรรทัด 2)
+---------------------------------------+  <- ฐาน Box 2 (VPOS + HEIGHT = 240)
```
จากแผนภาพ จะเห็นว่าพื้นที่ระหว่าง Y=160 ถึง Y=180 เป็นพื้นที่ที่ Box ทั้งสองทับซ้อนกัน (Overlap Zone) โมเดลจะไม่รู้เลยว่าพิกเซลในโซนนี้ (เช่น ยอดของสระ ี หรือฐานของสระ ู) ควรถูกจับคู่ (Align) เข้ากับข้อความของบรรทัดที่ 1 หรือบรรทัดที่ 2

**ตัวอย่างโค้ด ALTO XML ที่เก็บพิกัดทับซ้อนกัน (แสดงให้เห็นความผิดพลาด):**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<alto xmlns="http://www.loc.gov/standards/alto/ns-v4#">
  <Layout>
    <Page ID="Page_1" PHYSICAL_IMG_NR="1" HEIGHT="2000" WIDTH="1500">
      <PrintSpace HPOS="100" VPOS="100" WIDTH="1300" HEIGHT="1800">
        <TextBlock ID="TB_1" HPOS="100" VPOS="100" WIDTH="1300" HEIGHT="300">
          
          <!-- บรรทัดที่ 1: "ปู่ดูงู" -->
          <!-- พื้นที่แนวแกน Y: 100 ถึง 180 -->
          <TextLine ID="TL_1" HPOS="100" VPOS="100" WIDTH="500" HEIGHT="80">
            <String ID="ST_1" CONTENT="ปู่ดูงู" HPOS="100" VPOS="100" WIDTH="500" HEIGHT="80"/>
          </TextLine>

          <!-- บรรทัดที่ 2: "ที่นี่มี" -->
          <!-- พื้นที่แนวแกน Y: 160 ถึง 240 (สังเกตว่า 160 น้อยกว่า 180 ของบรรทัดบน!) -->
          <TextLine ID="TL_2" HPOS="100" VPOS="160" WIDTH="500" HEIGHT="80">
            <String ID="ST_2" CONTENT="ที่นี่มี" HPOS="100" VPOS="160" WIDTH="500" HEIGHT="80"/>
          </TextLine>

        </TextBlock>
      </PrintSpace>
    </Page>
  </Layout>
</alto>
```

### 2.4 การวิเคราะห์ความล้มเหลวของ Machine Learning เมื่อเจอ Overlap

โมเดล HTR/OCR ยุคแรก (ที่ใช้ Box-based attention mechanism) เมื่อได้รับข้อมูล Ground Truth ที่มีการ Overlap แบบนี้ จะเกิดปัญหา **"Attention Confusion"** กล่าวคือ เมื่อถึงเวลาสอนให้โมเดลอ่านบรรทัดที่ 1 น้ำหนัก (Weight) ของระบบจะพยายามกวาดสายตาลงมาเก็บรายละเอียดของสระ ู แต่กลับไปเจอปลายยอดของสระ ี ของบรรทัดที่ 2 ติดมาด้วย 

เมื่อเกิดขึ้นซ้ำๆ ในหลายๆ หน้า โมเดลจะเริ่มมีพฤติกรรม "เดาอักษรมั่ว" ข้ามบรรทัด เช่น แทรกวรรณยุกต์แปลกๆ เข้ามาในผลลัพธ์การอ่าน หรือสูญเสียสระล่างไปอย่างสมบูรณ์

การใช้ Bounding Box (สี่เหลี่ยมผืนผ้า) ใน ALTO ดั้งเดิม จึงได้รับการยืนยันแล้วว่า **ไม่เหมาะอย่างยิ่งกับภาษาไทย** หรือภาษาใดๆ ที่มีโครงสร้างซ้อนทับกันหลายระดับ (เช่น ภาษาอาหรับ ที่มีการตวัดหางข้ามเส้นอย่างวิจิตร)

## 3. การทำ Word Segmentation: ข้อจำกัดของแท็ก `<Word>` ใน PAGE/ALTO กับภาษาไทย

ทั้ง PAGE XML และ ALTO XML มีโครงสร้างเชิงลำดับชั้น (Hierarchical structure) ที่ออกแบบมาให้ผู้ใช้สามารถแบ่งย่อยข้อมูลลงไปได้ถึงระดับคำ (Word) และระดับตัวอักษร (Glyph) ได้ตามต้องการ

- โครงสร้าง **ALTO**: `<TextBlock>` -> `<TextLine>` -> `<String>` (เทียบเท่า Word)
- โครงสร้าง **PAGE**: `<TextRegion>` -> `<TextLine>` -> `<Word>`

### 3.1 ความพยายามในการตัดคำด้วย Visual Features

ในหน้าจอโปรแกรมสร้าง Ground Truth เช่น Aletheia หรือ eScriptorium (ยุคแรกๆ) ผู้ใช้สามารถใช้เมาส์ลากกรอบสี่เหลี่ยมคลุมทีละคำได้ สำหรับภาษาอังกฤษ การกำหนด `<Word>` ทำได้ง่ายมาก โดยอาศัยโปรแกรมคอมพิวเตอร์กวาดหาพื้นที่ว่างสีขาว (White space / Gap) เพื่อแยกคำออกจากกันอัตโนมัติ

แต่สำหรับภาษาไทย การจะแยกคำออกเป็น `<Word>` ในระดับ XML ต้องอาศัย **พจนานุกรม (Dictionary)** หรือ **โมเดลประมวลผลภาษาธรรมชาติ (NLP / Word Tokenizer)** เข้ามาช่วย ไม่สามารถดูแค่จากช่องว่างสีขาวบนภาพเพียงอย่างเดียวได้

### 3.2 ปัญหาทางภาษาศาสตร์และความกำกวม (Ambiguity)

แม้จะใช้ AI หรือ Dictionary มาช่วยตัดคำ ปัญหาคลาสสิกในการประมวลผลภาษาไทยก็ยังคงอยู่:

1. **ความกำกวมของการตัดคำ (Ambiguity)**: คำว่า "ตากลม" ตัดได้เป็น "ตา-กลม" (ตากลมโต) หรือ "ตาก-ลม" (เอาของไปตากลม) หากระบบอัตโนมัติตัดคำผิดตั้งแต่ขั้นตอนสร้าง XML ไฟล์ XML นั้นจะเก็บความผิดพลาดนี้ติดไปตลอดกาล
2. **ขอบเขตพิกัดภาพของคำที่ติดกัน (Overlapping Word Boundaries)**: แม้จะใช้ NLP ตัดคำว่า "ฉันกินข้าว" ออกเป็น "ฉัน" + "กิน" + "ข้าว" ได้ถูกต้องทางไวยากรณ์ แต่การจะหาพิกัด X, Y ว่าคำว่า "ฉัน" บนภาพพิกเซลจบลงที่ตำแหน่งใด และ "กิน" เริ่มต้นที่ตำแหน่งใด เป็นเรื่องยากมาก เพราะปลายหางของ น.หนู (จากคำว่าฉัน) อาจตวัดไปพันกับสระ ิ (จากคำว่ากิน) ทำให้การแบ่งพิกเซลออกเป็น 2 กล่องโดยไม่ทับซ้อนกันนั้นเป็นไปไม่ได้
3. **ปัญหาคำประสมและคำยืม**: ควรแยก "แม่น้ำ" เป็น "แม่" + "น้ำ" หรือไม่? ควรแยก "โรงเรียน" เป็น "โรง" + "เรียน" หรือไม่? มาตรฐานการจัดทำ Corpus แต่ละที่ (เช่น NECTEC Lexitron กับ Royal Institute) มีกฎการตัดคำที่ไม่ตรงกัน

### 3.3 ข้อจำกัดทางสถาปัตยกรรมของ PAGE XML และ ALTO XML ระดับ Word

จากข้อมูล **Verified Data**: "ส่งผลต่อระดับ `<Word>` ใน PAGE XML ทำให้ segmentation ระดับคำทำได้ยาก มักทำแค่ระดับ `<TextLine>`"

แนวปฏิบัติสากลในปัจจุบันสำหรับโครงการ Digital Humanities ภาษาไทย แนะนำให้ **ยุติความพยายามในการใช้แท็ก `<Word>` หรือ `<String>`** แล้วผลักดันเนื้อหาทั้งหมดให้อยู่ภายใต้แท็ก `<TextLine>` ทันที

หากต้องการข้อมูลระดับ Word สำหรับการค้นหา ให้ไปทำในขั้นตอน **Semantic Encoding (เช่น TEI XML)** หรือเก็บไว้เป็น Index ในระบบฐานข้อมูลแยกต่างหาก

### 3.4 ตัวอย่างข้อผิดพลาดเมื่อพยายามใช้ `<Word>` ในภาษาไทย (Antipattern)

นี่คือตัวอย่างความพยายามที่ผิดพลาด (Antipattern) หากเราฝืนใช้แท็ก `<Word>` ใน PAGE XML สำหรับประโยค "ฉันกินข้าว" การแบ่งพิกัดจะถูกทำอย่างหยาบๆ ซึ่งก่อให้เกิดความสับสน

```xml
<!-- [ANTIPATTERN: อย่าทำแบบนี้กับภาษาไทย] -->
<!-- การแยกคำโดยพยายามสับแบ่งพิกัดภาพออกเป็นส่วนๆ (Word Segmentation in PAGE) -->
<TextLine id="line_001">
    <Coords points="100,200 400,200 400,250 100,250"/>
    
    <!-- ระบบอาจตัดคำผิดพลาดทางภาษาศาสตร์เป็น ฉั, นกิ, นข้า, ว -->
    <!-- และพิกัด X ก็ถูกเฉือนแบ่งอย่างไม่สมเหตุสมผล -->
    <Word id="word_001">
        <Coords points="100,200 150,200 150,250 100,250"/>
        <TextEquiv><Unicode>ฉั</Unicode></TextEquiv>
    </Word>
    <Word id="word_002">
        <Coords points="151,200 230,200 230,250 151,250"/>
        <TextEquiv><Unicode>นกิ</Unicode></TextEquiv>
    </Word>
    <Word id="word_003">
        <Coords points="231,200 350,200 350,250 231,250"/>
        <TextEquiv><Unicode>นข้า</Unicode></TextEquiv>
    </Word>
    <Word id="word_004">
        <Coords points="351,200 400,200 400,250 351,250"/>
        <TextEquiv><Unicode>ว</Unicode></TextEquiv>
    </Word>
    
    <TextEquiv>
        <Unicode>ฉันกินข้าว</Unicode>
    </TextEquiv>
</TextLine>
```
การจัดเก็บในลักษณะนี้สร้าง "หนี้สินทางเทคนิค (Technical Debt)" มหาศาล เนื่องจากโมเดล AI ใดๆ ที่นำไฟล์นี้ไป Train ระดับ Word จะเรียนรู้ว่า "นกิ" คือรูปทรงหนึ่งของภาษาไทย ซึ่งผิดหลักภาษาโดยสิ้นเชิง

## 4. Baseline-based segmentation: ทางออกของภาษาไทยใน HTR (Kraken)

จากปัญหาของ Bounding Box (ข้อ 2) ที่รับมือการซ้อนทับไม่ได้ และปัญหา Word Segmentation (ข้อ 3) ที่ความกำกวมมีสูงเกินไป เทคโนโลยี HTR (Handwritten Text Recognition) สมัยใหม่ โดยเฉพาะสถาปัตยกรรมระดับโลกอย่าง **Kraken** หรือ **Calamari** จึงเปลี่ยนกระบวนทัศน์ (Paradigm) โดยสมบูรณ์

แนวทางใหม่นี้คือการละทิ้ง "กล่องสี่เหลี่ยม (Box-based)" และหันมาใช้ **"เส้นฐาน (Baseline-based)"** เป็นจุดเริ่มต้นในการแกะรอยข้อความ

### 4.1 ความหมายและวิธีการตีเส้น Baseline ในภาษาไทย

Baseline คือ "เส้นฐาน" หรือเส้นนำสายตาที่รองรับตัวอักษร 
สำหรับภาษาไทย **"Verified Data"** ได้ให้กฎทองคำในการพิจารณาเส้น Baseline ไว้ดังนี้:

> "Baseline ในภาษาไทยควรยึดเส้นใต้พยัญชนะหลัก (ไม่รวมสระล่าง เช่น ุ ู)"

**หลักการปฏิบัติที่ถูกต้อง:**
1. ลากเส้นจากซ้ายไปขวา (ตามทิศทางการอ่าน)
2. วางเส้นให้แนบชิดใต้ฐานของพยัญชนะ (ก, ข, ค, ..., ฮ) และสระในระดับเดียวกัน (เ, แ, โ)
3. เมื่อพบสระล่าง (ุ, ู) หรือเครื่องหมายพินทุ (ฺ) **ห้าม** หักเส้นเลี้ยวหลบลงไปด้านล่าง ให้ลากตัดทะลุ หรือข้ามผ่านสระล่างเหล่านั้นไปเลย เหมือนมันไม่มีตัวตนอยู่ในมิติแกน Y

**แผนภาพแสดง Baseline ที่ถูกต้องในภาษาไทย:**

```text
       เหนือวรรณยุกต์ ->    ้           ่               ๊      
       สระบน        ->    ี           ี               ิ      
       พยัญชนะหลัก   ->  ผ  ด  ก    ท  น      ช  า  ต        
========================================================= <- Baseline (เส้นฐาน) ลากตรง
       สระล่าง       ->  ู                           ุ      
```
*สังเกตว่าเส้นขนาน (Baseline) สีแดงในจินตนาการ จะลากผ่านใต้ตัว ผ, ด, ก, ท, น, ช, า, ต โดยจะขีด "ตัดผ่าน" สระ ู และ ุ ไปอย่างเป็นเส้นตรง*

### 4.2 การเปลี่ยนแปลงกระบวนทัศน์จาก Box-based สู่ Baseline-based

เมื่อเปลี่ยนมาใช้ Baseline โมเดล HTR (เช่น Kraken) จะทำงานดังนี้:
1. โมเดลรับภาพเอกสารเข้ามา
2. โมเดลค้นหาและทำนายเส้น Baseline ทั้งหมดในหน้ากระดาษ (Baseline Detection)
3. เมื่อได้เส้น Baseline แล้ว โมเดลจะสร้างพื้นที่ Polygon (รูปหลายเหลี่ยม) ล้อมรอบ Baseline เหล่านั้นเองอัตโนมัติ โดยหลบหลีกพื้นที่ทับซ้อนด้วยอัลกอริทึม
4. โมเดลอ่านภาพพิกเซลตามแนวเส้น Baseline ทีละมิลลิเมตรจากซ้ายไปขวา แล้วทำนายตัวอักษร

### 4.3 การทำงานร่วมกันระหว่าง Baseline และ Polygon ใน PAGE XML

มาตรฐาน PAGE XML ได้รับการออกแบบมาเพื่อรองรับกระบวนทัศน์นี้อย่างสมบูรณ์ ด้วยการอนุญาตให้บันทึกทั้งแท็ก `<Baseline>` (พิกัดของเส้น) และ `<Coords>` (พิกัดของ Polygon รอบเส้นนั้น) ควบคู่กันไป

Polygon มีข้อดีเหนือ Bounding Box อย่างมหาศาล เพราะมันคือการจุดเชื่อมต่อพิกัดหลายสิบจุด (X1,Y1 -> X2,Y2 -> ... -> Xn,Yn) ทำให้เกิดรูปร่างอิสระ สามารถ "วาดคดเคี้ยวซิกแซก" เพื่อหลบสระบนและสระล่างของบรรทัดข้างเคียงได้ ขจัดปัญหาการ Overlap ได้อย่างสมบูรณ์แบบ

**ตารางที่ 4.1: เปรียบเทียบ Bounding Box (ALTO) กับ Baseline+Polygon (PAGE XML)**

| คุณสมบัติ | Bounding Box (ALTO แบบดั้งเดิม) | Baseline + Polygon (PAGE XML) |
| :--- | :--- | :--- |
| **รูปทรงขอบเขต** | สี่เหลี่ยมผืนผ้า (Rectangle) แข็งกระด้าง | รูปหลายเหลี่ยมอิสระ (Arbitrary Polygon) ยืดหยุ่น |
| **โครงสร้างข้อมูลพิกัด** | 4 ค่าคงที่ (X, Y, Width, Height) | จุด N จุดตามแนวขอบเขต (X1,Y1 X2,Y2 ... Xn,Yn) |
| **ความสามารถจัดการ Overlap** | ทำไม่ได้ เกิดการทับซ้อน 100% เมื่อมีสระยื่น | ทำได้สมบูรณ์แบบ วาดหลบหลีกสระได้อย่างอิสระ |
| **ความเข้ากันได้กับ HTR ยุคใหม่** | ต่ำ (ก่อให้เกิดปัญหา Attention Confusion) | สูงมาก (Kraken และ eScriptorium รองรับโดยตรง) |
| **การเก็บเส้นนำสายตา (Baseline)** | มาตรฐานเก่าๆ ไม่มีโครงสร้างนี้ ต้องอนุมานจาก Y | มีแท็ก `<Baseline>` แยกอย่างเป็นทางการ ชัดเจน |

## 5. แนวปฏิบัติ (Best Practices) ในการสร้างโครงสร้าง XML สำหรับภาษาไทยและ Non-Latin

เพื่อให้การทำงานกับเอกสารโบราณ เอกสารจดหมายเหตุ หรือสิ่งพิมพ์ภาษาไทย/Non-Latin ได้รับผลลัพธ์ที่ดีที่สุด ป้องกันข้อผิดพลาด (Technical Debt) ในการประมวลผลขั้นต่อไป นี่คือ 5 แนวปฏิบัติ (Best Practices) ที่สกัดจากข้อกำหนด **Verified Data**:

### 5.1 ใช้ PAGE XML Polygon แทน ALTO Bounding Box เพื่อเลี่ยง Overlap
ดังที่ได้วิเคราะห์อย่างละเอียด การใช้ ALTO แบบเดิมที่บังคับใช้กล่องสี่เหลี่ยม จะล้มเหลวเสมอสำหรับภาษาไทยที่มีสระซ้อนทับกันข้ามบรรทัด การเปลี่ยนมาใช้มาตรฐาน PAGE XML ที่รองรับแท็ก `<Coords points="..." />` ในรูปแบบ Polygon อิสระ จะช่วยให้การทำ Segmentation แม่นยำ ไม่ชนกัน และไม่สร้างความสับสนให้โมเดล AI 
*(หมายเหตุ: หากมีความจำเป็นต้องใช้มาตรฐาน ALTO จริงๆ ในโครงการ ปัจจุบัน ALTO เวอร์ชัน 4 ขึ้นไป เริ่มรองรับแท็ก `<Shape><Polygon>` แล้ว แต่เครื่องมือสร้าง Ground Truth ทั่วโลกก็ยังนิยมพิมพ์ผลลัพธ์เป็น PAGE XML มากกว่า)*

### 5.2 อาศัย Baseline-based segmentation เป็นแกนหลัก (Core Anchor)
เครื่องมือฝึกสอน AI อย่าง eScriptorium และโมเดลทำนายอย่าง Kraken หรือ Calamari ต่างใช้ Baseline เป็นแกนกลางในการคำนวณ เมื่อผู้เชี่ยวชาญ (Human Annotator) ลาก Baseline ได้ถูกต้อง โมเดลจะสามารถสร้างพื้นที่ Polygon รอบๆ ได้เอง การจัดเก็บไฟล์ XML สำหรับภาษาไทย จึงต้องบังคับให้มีแท็ก `<Baseline>` กำกับอยู่เสมอในทุกๆ ระดับของ `<TextLine>` ห้ามตกหล่น

### 5.3 การกำหนดเขต Ground Truth ระดับ TextLine เป็นหลัก
**หลีกเลี่ยงการพยายามทำ Word Segmentation (ตัดเป็นคำๆ) ในระดับไฟล์โครงสร้างกายภาพ (PAGE XML)** ปล่อยให้ข้อความทั้งหมดไหลต่อเนื่องกัน (Continuous string) ภายใต้แท็กย่อย `<TextEquiv><Unicode>` ของ `<TextLine>` หากโครงการวิจัยใดต้องการแยกคำ (Word Tokenization) เพื่อทำดัชนีสืบค้น แนะนำให้นำข้อความเหล่านั้นไปผ่านกระบวนการ NLP แล้วไปบันทึกโครงสร้างความหมายใน **TEI XML (Text Encoding Initiative)** ภายหลัง การฝืนตัดคำใน PAGE XML มีแต่จะทำให้พิกัดภาพผิดเพี้ยน

### 5.4 การจัดการ Unicode และปัญหา Normalization (NFC vs NFD)
นี่คือจุดบอดสำคัญที่วิศวกรข้อมูลมักมองข้ามในการสร้างแท็ก `<Unicode>` ของภาษาไทย:
- **ปัญหาสระอำ (ำ)**: ในระบบ Unicode Standard สระอำ สามารถถูกตีความได้ 2 รูปแบบ คือ:
  1. การเก็บแบบรหัสอักขระเดียวเบ็ดเสร็จ (`U+0E33` - THAI CHARACTER SARA AM)
  2. การเก็บแยกชิ้นส่วนเป็น นิคหิต (`U+0E4D`) ตามด้วย ลากข้าง (`U+0E32`) (พบมากในระบบ macOS เก่าๆ หรือการทำ NFD Normalization)
  **Best Practice**: ต้องทำการตกลงกันในโครงการให้ชัดเจน และควรบังคับทำ **Normalization Form C (NFC)** เพื่อรวมชิ้นส่วนให้เป็นรหัสเดียว (U+0E33) ก่อนบันทึกลง `<Unicode>` ในไฟล์ XML เสมอ เพื่อให้ระบบสืบค้น (Search engine) ไม่สับสน

### 5.5 การจัดการอักขระพิเศษ (พยัญชนะไม่มีฐาน)
- **พยัญชนะไม่มีฐาน (ญ ฐ)**: ในการแสดงผล (Rendering) ทางหน้าจอ เมื่อ ญ (`U+0E0D`) และ ฐ (`U+0E10`) เจอกับสระล่าง (เช่น สระ ุ) ตัวอักษรเหล่านี้จะถูกตัดฐานที่ห้อยอยู่ข้างล่างออก กลายเป็นรูปพิเศษที่ไม่มีฐาน (เช่น คำว่า "สัญญา" -> "สัญญุ")
- **ข้อควรระวังอย่างยิ่ง**: ในการถอดความ (Transcription) ลง XML **ห้าม** ควานหารหัส Unicode พิเศษที่ตัดฐานแล้วมาใส่เด็ดขาด ให้พิมพ์พยัญชนะ ญ และ ฐ รูปแบบปกติร่วมกับสระล่างไปเลย (ใช้หลัก Diplomatic transcription พิมพ์ตามความหมายที่เห็น) ปล่อยให้เอนจินของฟอนต์ (Font Rendering Engine / HarfBuzz) ทำหน้าที่ปรับรูปตัดฐานในการแสดงผลหน้าจอด้วยตัวเอง

## 6. อภิธานศัพท์ (Glossary)

เพื่อความเข้าใจที่ตรงกันในงาน Digital Humanities ทางทีมงานได้รวบรวมศัพท์เทคนิคที่เกี่ยวข้อง ดังนี้:

- **Bounding Box**: กล่องสี่เหลี่ยมผืนผ้าที่ครอบตัวอักษรหรือข้อความ มักอ้างอิงด้วย X, Y, Width, Height
- **Polygon**: รูปหลายเหลี่ยมที่สร้างจากจุดพิกัดหลายจุด (X,Y) ใช้ตีกรอบล้อมข้อความที่มีรูปร่างไม่สม่ำเสมอ
- **Baseline**: เส้นฐานที่รองรับตัวอักษร เป็นแกนอ้างอิงสำคัญในเทคโนโลยี HTR ปัจจุบัน
- **Word Tokenization**: กระบวนการตัดคำในภาษาที่ไม่มีช่องว่างระหว่างคำ (เช่น ภาษาไทย) โดยใช้โมเดล NLP
- **NFC (Normalization Form Canonical Composition)**: กระบวนการรวมรหัส Unicode ของตัวอักษรและสระให้เป็นรหัสเดียว (เช่น สระอำ)
- **NFD (Normalization Form Canonical Decomposition)**: กระบวนการแยกรหัส Unicode ของอักขระเดี่ยวออกเป็นชิ้นส่วน (เช่น แยกสระอำ เป็น นิคหิต + ลากข้าง)
- **Diplomatic Transcription**: การถอดความโดยรักษาอักขระและการสะกดให้ตรงตามต้นฉบับทุกประการ รวมถึงความผิดพลาดหรืออักขระโบราณ
