## 1. ข้อดีของ ALTO XML

การเลือกใช้ **ALTO XML** (Analyzed Layout and Text Object) ในโปรเจกต์มีข้อได้เปรียบที่สำคัญหลายประการ 
โดยเฉพาะอย่างยิ่งเมื่อพิจารณาในบริบทของการสร้างห้องสมุดดิจิทัล (Digital Libraries) ระดับชาติ 
และกระบวนการเปลี่ยนผ่านเอกสารสิ่งพิมพ์ไปสู่ระบบดิจิทัล (Digitization) ในสเกลขนาดใหญ่

### 1.1 ความเป็นมาตรฐานในวงการห้องสมุดและเอกสารดิจิทัล (Library Standard)

- **เหตุผล**: 
  ALTO ถูกถ่ายโอนการดูแลจาก CCS GmbH ไปยัง **Library of Congress** ในปี 2009 
  และปัจจุบันมี **ALTO Editorial Board** เป็นผู้กำหนดทิศทาง ทำให้เกิดความเชื่อมั่นในแง่ของความเสถียร (Stability) และการสนับสนุนในระยะยาว 
  รูปแบบถูกออกแบบมาให้เข้ากันได้กับการจัดการไฟล์ดิจิทัลในระยะยาว (Long-term Preservation) 
  นอกจากนี้ยังทำงานร่วมกับมาตรฐาน **METS** (Metadata Encoding and Transmission Standard) ได้อย่างไร้รอยต่อ

- **ตัวอย่างสถานการณ์จริง**: 
  เมื่อสถาบันระดับชาติเช่นหอสมุดแห่งชาติ ต้องทำ digitization ให้กับหนังสือพิมพ์เก่าจำนวนมหาศาล 
  ระบบ archive ต้องสามารถเก็บข้อมูล metadata การประมวลผล ภาพสแกนต้นฉบับ และเนื้อหาข้อความ 
  ALTO ตอบโจทย์เรื่องนี้ได้ด้วยโครงสร้าง `<Description>` ที่ครบถ้วน

- **สถาบันที่ใช้**: 
  - Library of Congress (อเมริกา) ในโครงการ Chronicling America
  - British Library (สหราชอาณาจักร)
  - Bibliothèque nationale de France (ฝรั่งเศส)
  - National Library of Australia (Trove)
  - Swedish National Archives (Riksarkivet)

```xml
<!-- ตัวอย่างการใช้งานคู่กับ METS เชิงสถาปัตยกรรม (Conceptual) -->
<mets:fileSec>
  <mets:fileGrp ID="ALTO">
    <mets:file ID="ALTO_001" MIMETYPE="text/xml">
      <mets:FLocat LOCTYPE="URL" href="page_001.xml"/>
    </mets:file>
  </mets:fileGrp>
</mets:fileSec>
```

### 1.2 ระบบพิกัดแบบ Bounding Box ที่จัดการง่าย (Simple Coordinate System)

- **เหตุผล**: 
  การเก็บข้อมูลพิกัดด้วย `HPOS` (Horizontal Position), `VPOS` (Vertical Position), 
  `WIDTH` (ความกว้าง), `HEIGHT` (ความสูง) เป็นวิธีที่ประหยัดพื้นที่และตรงไปตรงมามาก 
  ทำให้นักพัฒนาสามารถดึงข้อมูลพิกัดสี่เหลี่ยม (Rectangle Bounding Box) เพื่อไปวาดกล่องบนหน้าเว็บ
  หรือรูปภาพได้อย่างง่ายดาย โดยไม่ต้องมีไลบรารีคำนวณทางเรขาคณิตเพิ่มเติม

- **ตัวอย่างสถานการณ์จริง**: 
  นักพัฒนาเว็บไซต์ห้องสมุดต้องการสร้างระบบ "Highlight ข้อความ" (Text Highlighting) เมื่อผู้ใช้ค้นหาคำเจอ 
  การเขียน JavaScript หรือ CSS เพื่อวาดกล่องสี่เหลี่ยมจาก attribute ทั้ง 4 ค่า 
  สามารถทำได้รวดเร็ว และใช้ทรัพยากรการประมวลผลของเบราว์เซอร์ (Browser Rendering) ต่ำมาก

- **สถาบันที่ใช้**: 
  - Koninklijke Bibliotheek (KB, เนเธอร์แลนด์) บนแพลตฟอร์ม Delpher

```xml
<!-- ตัวอย่างพิกัด Bounding Box ใน ALTO -->
<String ID="S1" CONTENT="Library" HPOS="100" VPOS="200" WIDTH="150" HEIGHT="40"/>
```

### 1.3 การจัดเก็บ Metadata เชิงกระบวนการผลิตอย่างครบวงจร (Comprehensive Metadata Integration)

- **เหตุผล**: 
  โครงสร้าง `<Description>` มีบล็อก `<Processing>` ที่ยอมให้ผู้ใช้บันทึกประวัติการผลิตไฟล์ได้อย่างละเอียดยิบ 
  ตั้งแต่การประมวลผลก่อนเข้า OCR (`<preProcessingStep>`), ขั้นตอน OCR (`<ocrProcessingStep>`), 
  ไปจนถึงหลังการทำ OCR (`<postProcessingStep>`) ทำให้สามารถตรวจสอบย้อนกลับ (Traceability) ได้ว่าใช้ซอฟต์แวร์เวอร์ชันใดในการสกัดข้อความ

- **ตัวอย่างสถานการณ์จริง**: 
  หากห้องสมุดค้นพบว่าข้อความที่สกัดด้วย Tesseract เวอร์ชัน 3.0 มีปัญหาความแม่นยำต่ำ 
  สามารถคิวรี XML หาไฟล์ทั้งหมดที่มี `<softwareVersion>3.0</softwareVersion>` 
  เพื่อนำมารัน OCR ใหม่ได้โดยไม่กระทบไฟล์ที่สกัดด้วยเวอร์ชันที่ใหม่กว่า

- **สถาบันที่ใช้**: 
  - หอจดหมายเหตุแห่งชาติและหน่วยงานที่ต้องการความแม่นยำด้าน Audit Trail

```xml
<!-- ตัวอย่างการเก็บประวัติ Software -->
<Processing>
  <ocrProcessingStep>
    <processingSoftware>
      <softwareName>Tesseract</softwareName>
      <softwareVersion>4.0</softwareVersion>
    </processingSoftware>
  </ocrProcessingStep>
</Processing>
```

### 1.4 การจัดการฟอนต์และรูปแบบข้อความที่ละเอียด (Detailed Font & Style Management)

- **เหตุผล**: 
  โครงสร้างของ ALTO มี `<Styles>` ที่แยกส่วนออกมาอย่างชัดเจนไว้ที่หัวไฟล์ 
  สามารถระบุ `FONTFAMILY`, `FONTSIZE`, และ `FONTSTYLE` ได้ครบถ้วน 
  ไม่ว่าจะเป็น bold, italics, subscript, superscript, smallcaps, underline หรือกระทั่ง strikethrough (รองรับในเวอร์ชัน 4.2 เป็นต้นไป)

- **ตัวอย่างสถานการณ์จริง**: 
  การแปลงหนังสือวิชาการ นิตยสารเก่า หรือเอกสารทางกฎหมายที่มีการเน้นคำ (Italic) และตัวยก (Superscript) 
  การใช้ ALTO ช่วยให้รักษาการจัดรูปแบบดั้งเดิมไว้ได้ เพื่อให้ผู้อ่านทราบว่าคำใดในเอกสารต้นฉบับถูกเน้นความสำคัญ

- **สถาบันที่ใช้**: 
  - Europeana และ Europeana Newspapers ที่ต้องแสดงผลหนังสือพิมพ์โบราณที่มีลูกเล่นการพิมพ์หลากหลายจากยุโรป

```xml
<!-- ตัวอย่างการนิยาม TextStyle -->
<Styles>
  <TextStyle ID="font1" FONTFAMILY="Times" FONTSIZE="12" FONTSTYLE="bold italics"/>
</Styles>
<TextBlock>
  <TextLine>
    <String CONTENT="Important" STYLEREFS="font1" ID="s2" HPOS="10" VPOS="10" WIDTH="50" HEIGHT="15"/>
  </TextLine>
</TextBlock>
```

### 1.5 กระบวนการทำงานที่แพร่หลายและกว้างขวาง (Wide Adoption in Digitization Pipelines)

- **เหตุผล**: 
  เครื่องมือพื้นฐานอย่าง **Tesseract OCR** สามารถส่งออกไฟล์เป็น ALTO ได้โดยตรง (ตั้งแต่เวอร์ชัน 4.0) 
  โดยไม่ต้องพึ่งพา script ภายนอกในการแปลงไฟล์ (Native Export) สิ่งนี้ช่วยลดความซับซ้อนใน Pipeline ลงไปได้มาก

- **ตัวอย่างสถานการณ์จริง**: 
  นักวิจัยที่มีงบประมาณและเวลาจำกัด ต้องการรัน OCR จำนวน 10,000 หน้าบนคอมพิวเตอร์ส่วนตัว 
  เขาสามารถเขียน Bash Script สั้นๆ โดยใช้ flag `tesseract input.tif output alto` 
  แล้วได้ไฟล์ที่พร้อมนำไปใช้งานหรือจัดแสดงบนหน้าเว็บได้ทันที

- **สถาบันที่ใช้**: 
  - HathiTrust Digital Library และโปรเจกต์ Digitization ขนาดเล็กถึงกลาง

## 2. ข้อเสียของ ALTO XML

แม้จะมีความแข็งแกร่งในแง่ของความเป็นมาตรฐานสำหรับการจัดเก็บถาวร แต่ ALTO ก็มีจุดอ่อนเมื่อต้องเผชิญกับเอกสารที่มีความซับซ้อน หรือต้องใช้ในงานวิจัยแนว HTR (Handwritten Text Recognition)

### 2.1 ความละเอียดของระบบพิกัดจำกัด (Limited Coordinate Precision)

- **ปัญหาจริง**: 
  Bounding Box ที่เป็นกรอบสี่เหลี่ยมผืนผ้า (Rectangle) ไม่สามารถครอบคลุมข้อความที่ถูกเขียนเอียง 
  มีลักษณะโค้งงอ หรือเบี้ยว (Skewed) ได้อย่างแม่นยำ ทำให้กรอบครอบคลุมพื้นที่ว่างเกินความจำเป็น

- **ผลกระทบ**: 
  นำไปสู่ปัญหา "Text Drift" หรือ "Overlap" ของกล่องข้อความเมื่อวาดทับบนภาพต้นฉบับ 
  ทำให้การนำข้อมูลไปฝึกสอน AI (Model Training) ทำได้ยาก เพราะ AI จะสับสนกับ Noise หรือเศษหมึกที่หลุดเข้ามาในกรอบสี่เหลี่ยม

- **Workaround**: 
  การใช้ `BASELINE` แบบ lists of points (เพิ่มในเวอร์ชัน 4.2) เพื่อช่วยบอกเส้นฐาน 
  หรือทำการ Deskew (หมุนปรับหน้าตรง) ตั้งแต่ก่อนทำ OCR

### 2.2 ความซับซ้อนของการจัดเก็บโครงสร้างเนื้อหาแบบแบน (Flat Structure vs Hierarchical Regions)

- **ปัญหาจริง**: 
  ALTO เก็บเนื้อหาในบล็อกแบบกว้างๆ (เช่น `<TextBlock>`) แต่ไม่ซ้อนลึกลงไปเป็นโครงสร้างทางความหมายแบบเชิงลึกหรือ Hierarchical

- **ผลกระทบ**: 
  ขาดความยืดหยุ่นในการจัดกลุ่ม (Grouping) หรือระบุส่วนประกอบย่อยของหน้าเอกสารที่มีความซับซ้อนสูง 
  เช่น โครงสร้างตาราง (Table) ที่มีเซลล์ทับซ้อนกัน หรือการจัด Layout เชิงลึกที่มี Callout box ซ้อนใน Paragraph

- **Workaround**: 
  ผู้ใช้มักจะต้องใช้ `<ComposedBlock>` เข้ามาช่วยจัดกลุ่ม แต่ก็ไม่อาจเทียบเท่าความอิสระของ Region ต่างๆ ใน PAGE XML 
  นอกจากนี้ยังต้องพึ่งพา `TAGREFS` โยงไปหา `<StructureTag>` ทำให้ไฟล์ซับซ้อนขึ้น

### 2.3 การจัดการองค์ประกอบที่ไม่ใช่ข้อความได้น้อยกว่า (Fewer Non-Text Elements)

- **ปัญหาจริง**: 
  ALTO มีบล็อกหลักๆ จำกัด เช่น Text, Composed, Illustration และ Graphical Element ไม่มี Region ย่อยที่เจาะจงเฉพาะ

- **ผลกระทบ**: 
  ไม่สามารถระบุความแตกต่างของบล็อกกราฟิกเฉพาะทางได้อย่างละเอียด 
  เช่น สูตรคณิตศาสตร์ (Math Equation), โน้ตเพลง (Musical Score), หรือแม้แต่บริเวณที่มีสัญญาณรบกวน (Noise/Artifacts)

- **Workaround**: 
  ต้องตั้งค่า ID พิเศษ หรือใส่ `<OtherTag>` กำกับไว้ ทำให้มาตรฐานการอ่านข้อมูลเหล่านี้อาจผิดเพี้ยนไปเมื่อต่างโปรเจกต์กันนำไฟล์ไปใช้ (Interoperability issues)

### 2.4 การจัดการลำดับการอ่าน (Reading Order) ที่อาจสับสนในเวอร์ชันเก่า

- **ปัญหาจริง**: 
  ก่อนหน้าเวอร์ชัน 4.3 ลำดับการอ่านต้องอาศัย "ลำดับการปรากฏของ XML element ในไฟล์" (Implicit Order) เป็นหลัก

- **ผลกระทบ**: 
  เมื่อเจอเอกสารหลายคอลัมน์ หนังสือพิมพ์ที่มีบทความข้ามคอลัมน์ หรือมีการจัดหน้าแบบ Magazine 
  การอ่านข้อความจากซ้ายไปขวา บนลงล่าง แบบตรงไปตรงมา จะทำงานผิดพลาดและเนื้อหาจะสลับกันมั่ว

- **Workaround**: 
  ใน ALTO v4.3 เป็นต้นไป (ออกเมื่อมิถุนายน 2022) ได้เพิ่ม `<ReadingOrder>` ที่ประกอบด้วย 
  `<OrderedGroup>`, `<UnorderedGroup>`, และ `<ElementRef>` เข้ามาแก้ไขปัญหานี้ 
  แต่อุปกรณ์รุ่นเก่ายังคงใช้ ALTO v2 หรือ v3 เป็นส่วนใหญ่

## 3. ข้อดีของ PAGE XML

**PAGE XML** (Page Analysis and Ground-truth Elements) ถูกพัฒนาขึ้นโดย PRImA Research Lab 
จากความต้องการแก้ปัญหาทางวิศวกรรมในการฝึกสอนและประเมินผล AI

### 3.1 ความแม่นยำสูงด้วยระบบพิกัด Polygon (High Precision Polygon Coordinates)

- **เหตุผล**: 
  นอกเหนือจาก `<Baseline>` แล้ว PAGE XML โดดเด่นที่การใช้ `<Coords>` ควบคู่กับ attribute `points="x1,y1 x2,y2 x3,y3 ..."` 
  ซึ่งสามารถวาดรูปหลายเหลี่ยม (Polygon) แนบสนิทไปตามรูปร่างของข้อความได้

- **ตัวอย่างสถานการณ์จริง**: 
  เอกสารจดหมายเหตุลายมือที่เขียนเอียง บรรทัดตก หรือมีข้อความแทรกตามขอบกระดาษ (Marginalia) 
  ระบบสามารถใช้วิธี Segmentation ลากกรอบหยักๆ วาดตามรูปร่างขอบเขตข้อความได้อย่างแนบเนียน 
  ไม่มีพื้นที่ว่างที่เกินมาไปรบกวนบรรทัดอื่น

- **สถาบันที่ใช้**: 
  - โครงการ OCR-D (เยอรมนี) 
  - ผู้เข้าร่วมแข่งขัน ICDAR competition

```xml
<!-- ตัวอย่างพิกัด Polygon ใน PAGE XML -->
<TextLine id="line_1">
  <Coords points="112,234 567,234 560,300 115,295"/>
  <Baseline points="112,280 567,280"/>
  <TextEquiv>
    <Unicode>Example of high precision</Unicode>
  </TextEquiv>
</TextLine>
```

### 3.2 โครงสร้างลำดับชั้นที่ลึกและละเอียด (Deep Hierarchical Structure)

- **เหตุผล**: 
  โครงสร้างแบบ `Region -> TextLine -> Word -> Glyph` ทำให้สามารถเก็บข้อมูลและวิเคราะห์ได้ตั้งแต่ระดับใหญ่สุด 
  ไปจนถึงสเกลเล็กสุดที่ระดับอักขระเดี่ยว (Glyph) โดยแต่ละระดับสามารถมี `<Coords>` (กรอบพิกัด) 
  และ `<TextEquiv>` (ผลลัพธ์ข้อความ พร้อมค่าความมั่นใจ Conf) แยกอิสระจากกัน

- **ตัวอย่างสถานการณ์จริง**: 
  ในการสร้างเครื่องมือ HTR (Handwritten Text Recognition) นักวิจัยต้องการทราบว่าโมเดลทำผิดพลาดที่อักขระ "s" หรือ "f" 
  ข้อมูลระดับ Glyph ground-truth ช่วยให้นักวิจัยวินิจฉัยและ Fine-tune โมเดลได้อย่างแม่นยำ

- **สถาบันที่ใช้**: 
  - Transkribus community ซึ่งมีฐานผู้ใช้งานมากกว่า 100,000 คน

### 3.3 ประเภท Region ที่หลากหลายครอบคลุม (Extensive Region Types)

- **เหตุผล**: 
  PAGE เตรียมประเภทพื้นที่ไว้ครบถ้วนแบบพร้อมใช้งาน (Out of the box) เช่น 
  `<TextRegion>` (พร้อม subtype: heading, paragraph, caption, footnote, etc.), 
  `<ImageRegion>`, `<GraphicRegion>`, `<TableRegion>`, `<MathsRegion>`, 
  `<ChemRegion>`, `<MusicRegion>`, `<AdvertRegion>`, และกระทั่ง `<NoiseRegion>`

- **ตัวอย่างสถานการณ์จริง**: 
  การทำ Digitization เอกสารวิทยาศาสตร์ หรือตำราเรียนเก่า ซึ่งมีทั้งเนื้อหา สูตรเคมี กราฟคณิตศาสตร์ 
  โมเดล AI (เช่น YOLO หรือ Mask R-CNN) สามารถถูกสอนให้ดึงโซนเหล่านี้แยกกันตั้งแต่ตอนทำ Layout Analysis

- **สถาบันที่ใช้**: 
  - HTR-United network และชุมชนนักวิจัย

### 3.4 การรองรับระบบ Custom Attribute (Custom Attribute System Support)

- **เหตุผล**: 
  PAGE อนุญาตให้นำเข้า attribute แบบ `custom` ใน element ต่าง ๆ ได้อย่างถูกหลัก Schema Validation 
  (เช่น `custom="structure {type:heading;}"`) เปิดกว้างสำหรับการต่อยอดเชิงลึก

- **ตัวอย่างสถานการณ์จริง**: 
  แพลตฟอร์ม Transkribus ใช้ attribute custom ในการใส่ tag เฉพาะทาง 
  เช่น `custom="readingOrder {index:0;}"` หรือการมาร์กผู้เขียน มาร์กสีน้ำหมึก (Ink type) เข้าไปในบรรทัดได้ทันที

- **สถาบันที่ใช้**: 
  - แพลตฟอร์ม eScriptorium และ Transkribus

### 3.5 ความยืดหยุ่นในระบบ Baseline (Flexible Baseline System)

- **เหตุผล**: 
  PAGE ให้ความสำคัญกับ `<Baseline>` อย่างจริงจัง โดยแยกออกมาเป็น element หลักควบคู่กับ `Coords`
  ทำให้ AI สมัยใหม่ที่ทำงานในรูปแบบ "Line-level" (เช่น Calamari, PyLaia) 
  สามารถอ้างอิงเส้นบรรทัดเพื่อดึงภาพมาประมวลผลได้อย่างมีประสิทธิภาพ

- **ตัวอย่างสถานการณ์จริง**:
  เอกสารที่เป็นใบลาน มีบรรทัดที่โค้งตามลายไม้ การลากเส้น Baseline โค้งตามตัวอักษร 
  แล้วให้โมเดล AI "คลี่" (dewarp) ภาพรอบเส้น Baseline ออกมาเป็นภาพบรรทัดตรงก่อนทำ Recognition 
  เป็นเทคนิคสำคัญที่ต้องพึ่งพา PAGE XML

- **สถาบันที่ใช้**:
  - ศูนย์วิจัยมหาวิทยาลัยต่าง ๆ ด้าน Digital Humanities ทั่วโลก

## 4. ข้อเสียของ PAGE XML

แม้ PAGE จะมีฟีเจอร์ระดับสูง (Advanced Features) ตอบโจทย์งานวิจัย 
แต่ความยืดหยุ่นเหล่านั้นก็มาพร้อมกับราคาที่ต้องจ่ายในด้านความซับซ้อนทางวิศวกรรม

### 4.1 ความซับซ้อนสูงในการสร้างและประมวลผล (High Complexity in Generation and Parsing)

- **ปัญหาจริง**: 
  โครงสร้างที่มีระดับชั้นมากมาย (Nesting) และพิกัดแบบ Polygon ที่มีจุดร้อยเรียงกันยาวเหยียด 
  ทำให้การแกะ (Parse) และเขียน (Generate) XML ยุ่งยากกว่า ALTO

- **ผลกระทบ**: 
  Developer หน้าใหม่มักใช้เวลาเรียนรู้นาน (Steep Learning Curve) 
  นอกจากนี้หากใช้สคริปต์ทำ Regex แทนการใช้ XML Parser จะมีโอกาสพังง่ายมาก

- **Workaround**: 
  แนะนำให้หลีกเลี่ยงการเขียนโค้ดจัดการ XML ดิบ แต่ให้เปลี่ยนไปใช้ไลบรารีเฉพาะทาง 
  เช่น `pypxml` ใน Python หรือ Java API ของทาง PRImA แทน

### 4.2 ขนาดไฟล์ที่อาจใหญ่กว่ามหาศาล (Potentially Bloated File Size)

- **ปัญหาจริง**: 
  การระบุพิกัด Polygon อาจต้องใช้พิกัดระดับ 50-100 จุดต่อหนึ่งเส้น (TextLine) 
  ลองจินตนาการว่าหากหน้ากระดาษมี 40 บรรทัด และยังแบ่งระดับคำ (Word) และอักขระ (Glyph) อีก 
  ตัวอักษรทุกตัวล้วนมี Polygon ยาวเหยียดของตัวเอง

- **ผลกระทบ**: 
  ขนาดไฟล์อ้วนและใหญ่ (Bloated File Size) ใหญ่กว่า ALTO XML ปกติหลายสิบเท่า 
  ซึ่งส่งผลถึงต้นทุนพื้นที่ Storage Bandwidth แบนด์วิดท์เครือข่าย และความอืดของ Database

- **Workaround**: 
  ผู้ใช้งานสามารถใช้เทคนิค Polygon Simplification (เช่นอัลกอริทึม Ramer-Douglas-Peucker) 
  เพื่อลดจุดที่วาดโดยไม่สูญเสียรูปทรงมากนัก หรือลดความละเอียดระดับอักขระ (Glyph level) ทิ้งไปหากไม่ได้ใช้

### 4.3 การจัดเก็บ Metadata ไม่เป็นมาตรฐานระดับห้องสมุด (Less Library-Standard Metadata)

- **ปัญหาจริง**: 
  โครงสร้าง `<Metadata>` ของ PAGE (เช่น `<Creator>`, `<Created>`, `<LastChange>`) 
  ออกแบบมาเพื่อบริหารจัดการสถานะไฟล์ (Ground truth management) เป็นหลัก 
  ไม่ได้มีบล็อกบันทึกกระบวนการทำงาน OCR หลายเลเยอร์ และรายละเอียดตัวซอฟต์แวร์แบบลึกซึ้งเท่า `<Description>` ของ ALTO

- **ผลกระทบ**: 
  สถาบันความทรงจำระดับชาติด้าน Archival Sciences มองว่า PAGE 
  ไม่เพียงพอสำหรับการเก็บรักษาและอธิบาย Metadata ทางเทคนิคสำหรับการใช้ระยะยาว 50 ปีขึ้นไป

- **Workaround**: 
  จับคู่ PAGE XML เข้ากับมาตรฐานภายนอกอย่าง METS 
  หรือเก็บเป็น PAGE เพื่อทำ OCR พอได้ผลลัพธ์แล้วค่อย Export ออกมาเป็น ALTO 
  (ผ่านเครื่องมือเช่น `ocr-fileformat`) เพื่อส่งขึ้นคลังข้อมูล

### 4.4 เครื่องมือดั้งเดิมบางตัวไม่รองรับโดยตรง (Limited Direct Support in Legacy OCR Engines)

- **ปัญหาจริง**: 
  OCR ยอดนิยมแบบดั้งเดิม (เช่น Tesseract) ไม่ได้ออกแบบให้ Export PAGE XML natively

- **ผลกระทบ**: 
  ไม่สามารถทำ End-to-end pipeline ด้วย Tesseract โดดๆ ได้ 
  ต้องมีเครื่องมือรอยต่อในการ Format Conversion

- **Workaround**: 
  จำเป็นต้องเชื่อม (Chain) Pipeline เข้ากับ OCR-D 
  หรือใช้สคริปต์ภาษา Python เสริมเพื่อหุ้ม hOCR กลับมาเป็น PAGE (เช่น `pagexml-tools`)

## 5. เปรียบเทียบจากมุมมองต่าง ๆ

ในการเลือกนำไปใช้งาน การทำความเข้าใจ "ผู้ที่มีส่วนได้ส่วนเสีย (Stakeholders)" 
สำคัญกว่าการเทียบเชิงเทคนิคล้วนๆ

### 5.1 มุมมองนักวิจัย HTR และ Digital Humanities (DH)
> **ผู้ชนะ: PAGE XML**

นักวิจัยที่ศึกษาด้านตัวอักษรโบราณ และการสแกนลายมือ 
มองว่า PAGE XML เป็นฮีโร่ เพราะรองรับ Ground Truthing ละเอียดสุดขั้ว 
สามารถเก็บค่า Confidence ในแต่ละตัวอักษร, มี Region เฉพาะเช่น `<TableRegion>`, `<MathsRegion>` 
ซึ่ง ALTO ไม่มี นักวิจัยต้องการ Data ที่มีคุณค่าเพื่อสอน AI ให้ทำงานได้ดีที่สุด

### 5.2 มุมมองบรรณารักษ์ห้องสมุดดิจิทัล (Digital Librarians)
> **ผู้ชนะ: ALTO XML**

บรรณารักษ์รับผิดชอบภาพรวม สเกลไฟล์ร้อยล้านไฟล์ และต้องเปิดให้อ่านได้ในอีก 30 ปีข้างหน้า 
มองว่า ALTO XML เป็นฮีโร่ เพราะมีเสถียรภาพ มีหน่วยงานรัฐรับรองคู่กับ METS 
บรรณารักษ์แคร์เรื่องการบำรุงรักษา ขนาดไฟล์ที่รับได้ และ Metadata ที่เก็บประวัติเครื่องสแกน 
มากกว่าพิกัดที่แม่นยำระดับ Polygon

### 5.3 มุมมอง Software Developer
> **ผู้ชนะ: เสมอกัน (ขึ้นกับเครื่องมือ)**

Developer ที่ทำ Web Viewer, Search Engine มองเป็นกลางแต่เอนเอียงไปทาง ALTO (สำหรับการแสดงผล): 
Developer ที่ทำ Web UI ชอบ ALTO เพราะ Bounding box สี่เหลี่ยม 4 ตัวแปรสร้างง่าย 
แต่ถ้าเป็น AI Developer ที่ต้องเทรนโมเดล (ML Engineer) 
จะรักความหลากหลายของเครื่องมือฝั่ง PAGE มากกว่า (Kraken, PyLaia, ocrd_models)

### 5.4 มุมมองผู้จัดการโปรเจกต์ Digitization ขนาดใหญ่ (Large-Scale Project Managers)
> **ผู้ชนะ: เลือกใช้ทั้งคู่แบบไฮบริด (Hybrid Strategy)**

ผู้จัดการโปรเจกต์ที่ดูแลกระบวนการตั้งแต่สแกน จนส่งมอบไฟล์ 
มักสั่งให้ทีมสกัดข้อมูลและฝึกสอนโมเดลทำงานบน **PAGE XML** เป็น "Working Format" 
เพราะเครื่องมือ Transkribus, eScriptorium ถนัดแบบนี้ 
แต่ในกระบวนการสุดท้าย (Final Archive) จะให้แปลงทั้งหมดไปเป็น **ALTO XML** (v4.3+) 
เพื่อประหยัดพื้นที่เซิร์ฟเวอร์และให้ห้องสมุดนำไปใช้ต่อได้อย่างสบายใจ

## 6. ตารางคะแนนเปรียบเทียบ

ตารางด้านล่างนี้เปรียบเทียบมาตรฐานทั้งสองด้วยเกณฑ์มากกว่า 20 ข้ออย่างละเอียด
(ใช้เกณฑ์: ดีมาก, ดี, ปานกลาง, จำกัด)

| หมวดหมู่ (Category) | เกณฑ์การเปรียบเทียบ (Criteria) | ALTO XML | PAGE XML | ข้อมูลเสริม / ข้อสังเกต |
| :--- | :--- | :--- | :--- | :--- |
| **โครงสร้างทางเรขาคณิต** | ความละเอียดของระบบพิกัด (Precision) | ปานกลาง (Bounding Box) | **ดีมาก (Polygon)** | PAGE แม่นยำกว่าด้วยเส้นรอบรูปอิสระลด Text Drift |
| | การระบุเส้นฐาน (Baseline) | ปานกลาง (พึ่งรองรับใน v4.2+) | **ดีมาก** | PAGE ให้ความสำคัญกับ Baseline เป็นแกนกลางมาแต่แรก |
| | หน่วยวัดพิกัด (Measurement Units) | **ดีมาก (Pixel, mm10, inch1200)**| ปานกลาง (มักใช้ Pixel) | ALTO เก็บพิกัดเทียบหน่วยกายภาพได้จริง |
| **การรองรับความซับซ้อน** | โครงสร้างข้อมูลเชิงลึก (Hierarchical) | จำกัด (Flat blocks) | **ดีมาก (Tree structure)** | PAGE จัดลำดับชัดเจน (Region -> Line -> Word -> Glyph) |
| | ลำดับการอ่าน (Reading Order) | ดี (มีใน v4.3+) | **ดีมาก** | PAGE มี OrderedGroup/UnorderedGroup แต่แรก |
| | การระบุประเภท Block / Region | ปานกลาง (Text, Image) | **ดีมาก (15+ ชนิด)** | PAGE แยก Math, Music, Map, Chem ได้ลึก |
| | การรองรับตาราง (Table recognition) | ปานกลาง (ComposedBlock) | **ดีมาก (TableRegion)** | PAGE เหมาะกับการสอน AI สกัดตาราง |
| | ประเภทของภาพรอง (Alternative Image)| จำกัด | **ดีมาก** | PAGE สั่งเก็บภาพ Binarized ขาวดำแนบมากับ Metadata ได้ |
| **ความเหมาะสมของชิ้นงาน**| การรองรับเอกสารโบราณ/ลายมือ (HTR) | ปานกลาง | **ดีมาก** | PAGE เป็นมาตรฐาน "De facto" ในวงการ HTR |
| | การรองรับสิ่งพิมพ์ทั่วไป (Newspaper) | **ดีมาก** | ดี | ALTO ครองตลาดหนังสือพิมพ์และ Text พื้นฐาน |
| | การรองรับเอกสารที่ใช้ Non-Latin | ดี | ดี | ใช้งานได้ดีทั้งคู่ผ่าน UTF-8 และ Attribute `LANG` |
| **วิศวกรรมข้อมูล** | ขนาดไฟล์ (File Size) | **ดี (ไฟล์มีขนาดกะทัดรัด)** | ปานกลาง (ไฟล์อาจใหญ่มาก) | พิกัด Polygon ทำให้ PAGE ใช้ Bandwidth ค่อนข้างเยอะ |
| | ความเร็วในการ Parsing (Speed) | **ดีมาก (โครงสร้างเบา)** | ปานกลาง (ต้องแกะปม Tree) | ALTO โหลดเร็วกว่าในระบบ Web rendering |
| | การรองรับ Custom Attribute | ปานกลาง | **ดีมาก (`custom`)** | PAGE ยอมให้นักวิจัยยัดค่าส่วนตัวเข้าไปง่ายๆ |
| | การจัดเก็บ Metadata เชิงเทคนิค | **ดีมาก (`<Description>`)** | ปานกลาง | ALTO เก็บประวัติซอฟต์แวร์ OCR ได้ระดับ Audit |
| **เครื่องมือและ Ecosystem** | รองรับ Native ส่งออกจาก Tesseract | **ดี (มี flag `-c alto`)** | จำกัด (ต้องมีตัวแปลง) | Tesseract สนิทกับ ALTO และ hOCR มากกว่า |
| | ระบบนิเวศ OCR-D Project | ปานกลาง (ใช้เป็นตัวส่งออก) | **ดีมาก (Primary format)** | OCR-D กำหนดให้ใช้ PAGE เป็นตัวส่งผ่านระหว่างโมดูล |
| | รองรับใน eScriptorium / Kraken | ดี | ดี | 2 แพลตฟอร์มนี้เก่งพอที่จะอ่านและเขียนได้ดีเยี่ยมทั้งคู่ |
| | รองรับใน Transkribus | ปานกลาง (ส่งออกเป็น v2) | **ดีมาก (Native)** | PAGE เกิดมาเพื่อเป็นหัวใจของ Transkribus |
| | เครื่องมือเสริมใน Python (Libraries) | ปานกลาง | **ดีมาก** | ฝั่ง PAGE มีชุมชน Python เขียน pypxml ให้ใช้อย่างล้นหลาม |
| **ภาพรวมโครงการ** | คุณภาพของ Documentation | **ดีมาก (จาก LoC)** | ดี (จาก PRImA) | ALTO มีตัวอย่าง XSD ที่อธิบายง่ายและชัดกว่าเล็กน้อย |
| | การเก็บรักษา (Long-term Preservation)| **ดีมาก** | ปานกลาง | โลกของ Archive เชื่อใจมาตรฐานที่มาจาก Library of Congress |
| | Backward Compatibility | **ดีมาก (Versioning ชัดเจน)** | ปานกลาง | PAGE มักมีอัปเดต Date-based ที่อาจทำให้ Parser เก่าพังได้ |
| | ขนาดของชุมชนผู้ใช้งาน (Community) | **ใหญ่มาก (ห้องสมุด)** | **ใหญ่มาก (วิจัย/AI)** | ต่างฝ่ายต่างเป็นผู้ยิ่งใหญ่ในเขตแดนของตน |

> [!TIP]
> หากต้องเลือกเพียง 1 รูปแบบ: 
> **เลือก ALTO XML** หากคุณทำโครงการห้องสมุด สิ่งพิมพ์ปกติ และไม่ต้องใช้โมเดล AI ล้ำลึกมาก
> **เลือก PAGE XML** หากเอกสารมีความซับซ้อนสูง เป็นลายมือ มีตาราง/กราฟเยอะ และตั้งเป้าฝึกโมเดล AI ของตัวเอง

## 7. กรณีศึกษา

การยกตัวอย่างสถาบันระดับโลก ช่วยให้เห็นภาพจริงว่าผู้ใช้งานระดับ "Enterprise" เลือกตัดสินใจอย่างไร

### 7.1 Chronicling America (Library of Congress, USA)

- **สถานการณ์ / วัตถุประสงค์**: 
  ต้องการแปลงหนังสือพิมพ์ประวัติศาสตร์ของอเมริกานับล้านหน้าให้อยู่ในรูปแบบดิจิทัลที่สืบค้นได้ผ่านอินเทอร์เน็ตให้ประชาชนทั่วไป
- **ตัดสินใจใช้ ALTO ทำไม**: 
  หนังสือพิมพ์ส่วนใหญ่มีรูปแบบการจัดหน้าที่ชัดเจนเป็นคอลัมน์และเป็นตัวพิมพ์ (Machine Print) 
  การใช้ Tesseract หรือ ABBYY สามารถสกัด ALTO แบบ Bounding box ได้รวดเร็ว ประหยัดเวลาและค่าใช้จ่าย 
  นอกจากนี้ Library of Congress เป็นหน่วยงานที่รับผิดชอบมาตรฐาน ALTO ด้วยตนเอง 
  ดังนั้นจึงสอดคล้องกับนโยบายภายใน
- **ผลลัพธ์**: 
  ได้ระบบฐานข้อมูลขนาดมหาศาล ที่สืบค้นคำได้ทันที พร้อมแสดง Highlight บนเบราว์เซอร์ได้รวดเร็ว 
  (เพราะไม่ต้องเรนเดอร์รูปทรง Polygon) ALTO ถูกจับคู่กับ METS เป็นคลังสมบัติของชาติที่มีความยั่งยืน

### 7.2 OCR-D Project (Germany)

- **สถานการณ์ / วัตถุประสงค์**: 
  รัฐบาลเยอรมัน (ผ่านงบประมาณของ DFG) สนับสนุนการนำเอกสารยุคฟื้นฟูศิลปวิทยาการ (VD16, VD17, VD18) 
  ที่มีตั้งแต่ภาษาละติน เยอรมันโบราณ (Fraktur) และมีหน้าตาประหลาด เช่น อักขระซ้อนทับ Marginalia มาแปลงเป็นข้อมูลคุณภาพสูง
- **ตัดสินใจใช้ PAGE ทำไม**: 
  OCR-D สถาปนาให้ "PAGE XML เป็น Format กลาง (Data Exchange Format) ตลอดทั้งสายการผลิต" 
  ไม่ว่าจะเป็นเครื่องมือทำ Binarization ตัดขอบ สกัดหน้า ล้วนต้องส่งต่อข้อมูลด้วย PAGE 
  เนื่องจากต้องพึ่งพาพิกัด Polygon ในการหลบหลีกภาพขอบหน้ากระดาษที่ฉีกขาด 
  และยังใช้ฟีเจอร์ `AlternativeImage` ในการส่งต่อภาพขาวดำไปยังสเตปต่อไปได้อย่างดี
- **ผลลัพธ์**: 
  เกิดเป็นมาตรฐานเปิดสำหรับ Workflow สายลึก (Processor chaining) นักพัฒนา 10 คนสามารถเขียน 10 โมดูลที่รับและส่ง PAGE XML ให้กันและกันได้อย่างไหลลื่น

### 7.3 eScriptorium Projects (EPHE-PSL University)

- **สถานการณ์ / วัตถุประสงค์**: 
  สร้างแพลตฟอร์ม Web-based สำหรับให้นักวิจัยและอาสาสมัคร (Crowdsourcing) เข้ามาช่วยกันถอดความเอกสารโบราณ 
  และฝึกโมเดล Kraken สำหรับเอกสารตั้งแต่ภาษาอาหรับ ฮีบรู ยันโบราณวัตถุ
- **ตัดสินใจรองรับทั้งสอง (Format Agnostic)**: 
  ผู้สร้างตระหนักดีว่า มีผู้ใช้งานที่เคยใช้ Transkribus (ไฟล์ PAGE) และผู้ใช้ที่มาจากห้องสมุดแห่งชาติ (ไฟล์ ALTO) 
  ดังนั้น eScriptorium จึงเปิดกว้าง รองรับได้เต็มรูปแบบทั้ง 2 นามสกุล โดยใช้ ID เป็นตัวจับคู่ Segment
- **ผลลัพธ์**: 
  แพลตฟอร์มเติบโตอย่างก้าวกระโดด ชุมชนผู้ใช้งานมีความสุขเพราะไม่มีกำแพงหรือการบังคับคอขวด (Vendor lock-in) อีกต่อไป

### 7.4 ตัวอย่างสถานการณ์จากทวีปเอเชีย (Asia Context)

- **สถานการณ์จริง**: 
  การทำ Digitization เอกสารอักษรธรรม อักษรขอม จารึกใบลาน หรือจดหมายเหตุภาษาไทย จีน ญี่ปุ่น 
  มีลักษณะของเส้นสายที่พริ้วไหว โค้งงอ และมักไม่มีการจัดหน้าแบบคอลัมน์กริดที่เป็นระเบียบ (Non-standard grid)
- **เครื่องมือที่ใช้ (ในมุมวิจัย)**: 
  ปัจจุบันพบว่านักวิจัยในเอเชียมักเริ่มนำ **PAGE XML** (โดยเฉพาะผ่านทางโปรแกรม Transkribus) 
  มาใช้เพื่อตีเส้น Baseline หักงอไปตามใบลาน (Curve Baseline) ซึ่งสร้าง Ground Truth ที่มีคุณภาพเหนือกว่าการใช้ ALTO XML แบบดั้งเดิม
- **[ข้อมูลจำกัด] ในวงการราชการ**: 
  ทว่าในภาคธุรกิจ (Commercial OCR) เพื่อแปลงเอกสารราชการพิมพ์ดีด หรือศูนย์จดหมายเหตุระดับรัฐ (National Archives) 
  ในเอเชียหลายแห่ง ยังคงคุ้นชินกับการใช้ไฟล์ PDF ที่ฝัง Invisible Text (PDF/A) หรือ ALTO XML ควบคู่ไปกับ hOCR เป็นหลัก 
  เนื่องด้วยความง่ายในการจ้างเหมาเอกชนทำสแกนเนอร์ที่แถมซอฟต์แวร์มาตรฐานมาให้
