## 1. ทำไมต้องแปลงรูปแบบ?

การจัดการเอกสารดิจิทัลที่มีโครงสร้างซับซ้อน (Digital Document Management) มักเกี่ยวข้องกับเครื่องมือหลายตัวในระบบนิเวศเดียวกัน ผู้ปฏิบัติงานมักพบกับความจำเป็นที่ต้องพึ่งพาการแปลงรูปแบบไฟล์ (Format Conversion) ระหว่างมาตรฐานต่างๆ โดยเฉพาะ PAGE XML และ ALTO XML ซึ่งเป็นสองมาตรฐานที่โดดเด่นที่สุดในวงการ OCR/HTR 

การแปลงรูปแบบนั้นไม่ใช่เป้าหมายในตัวเอง แต่เป็น "สะพานเชื่อม" เพื่อตอบสนองความต้องการในขั้นตอนที่แตกต่างกันของวงจรชีวิตข้อมูล

### สถานการณ์ที่ต้องแปลง (Scenarios Requiring Conversion)

ในระบบนิเวศการทำงานเอกสารดิจิทัล มักมีกรณีการใช้งานที่ระบบต้นทางและระบบปลายทางใช้มาตรฐานที่ต่างกัน และบีบบังคับให้ทีมงานต้องพึ่งพาเครื่องมือแปลงข้อมูล:

- **การประมวลผลระหว่างทาง (Working Pipeline) ถอยไปสู่การจัดเก็บระยะยาว (Long-term Archiving):**
  ในเฟสของการป้อนข้อมูล การจัดการเลย์เอาต์ (Layout Analysis) และการปรับแก้ด้วยมนุษย์ (Manual Transcription) โครงการส่วนใหญ่มักใช้เครื่องมือที่ถนัดที่สุดในการทำงาน เช่น เครื่องมือ eScriptorium, Transkribus, หรือชุดซอฟต์แวร์ของ OCR-D Framework เครื่องมือเหล่านี้มักสนับสนุน หรือผลิต PAGE XML เป็นหลัก เนื่องจาก PAGE XML มีความยืดหยุ่นในการจัดเก็บโครงสร้างที่ไม่แน่นอน 
  อย่างไรก็ตาม เมื่อโปรเจกต์สิ้นสุดลง และต้องการส่งมอบข้อมูลเข้าสู่คลังจัดเก็บดิจิทัล (Digital Repository) ของหอจดหมายเหตุแห่งชาติ หรือสถาบันห้องสมุดระดับนานาชาติ (เช่น Library of Congress, Europeana) ข้อกำหนดของสถาบันเหล่านี้มักจะระบุอย่างชัดเจนว่าต้องส่งมอบคอลเลกชันในรูปแบบ ALTO XML (มักควบคู่กับ METS) เนื่องจากเป็นมาตรฐานที่มีความเสถียรสำหรับการนำไปจัดแสดงผ่าน Viewer สาธารณะ ดังนั้นกระบวนการแปลง "PAGE เพื่อใช้งาน → ALTO เพื่อจัดเก็บ" จึงเกิดขึ้นเสมอ และเป็นความเจ็บปวดที่หลีกเลี่ยงไม่ได้ของทุกโครงการ

- **การนำชุดข้อมูลในอดีตกลับมาใช้ใหม่เพื่อการฝึกสอนโมเดล (Training Data Re-use for Machine Learning):**
  ในยุคของการฝึกฝนโมเดล AI ด้วยเทคโนโลยี Deep Learning (เช่น การใช้งาน Kraken, PyLaia, หรือโมเดลในเครือ Hugging Face) การมีข้อมูล Ground Truth ปริมาณมหาศาลคือหัวใจสำคัญ 
  หากห้องสมุดมีชุดข้อมูลหน้าหนังสือพิมพ์เก่าจำนวนมากที่เคยจัดเก็บเป็น ALTO XML ตั้งแต่เมื่อสิบปีที่แล้ว (เช่น ช่วงที่มีแต่ ALTO v2.0 ซึ่งมีข้อจำกัดหลายประการ) แต่ทีมนักวิจัยต้องการนำชุดข้อมูลนี้มาฝึกสอนโมเดลใหม่ในระบบที่ออกแบบมาให้บริโภคไฟล์ PAGE XML เป็นหลัก (เพราะต้องการความยืดหยุ่นของแท็กระดับสูงกว่า) การแปลง "ALTO เก่า → PAGE สำหรับฝึกโมเดล" จะช่วยประหยัดเวลาและงบประมาณมหาศาลโดยไม่ต้องจ้างคนมาทำพิมพ์ข้อความกำกับ (Ground Truth) ใหม่ตั้งแต่ต้น

- **การบูรณาการซอฟต์แวร์หลายค่าย (Multi-Vendor and Hybrid Pipelines):**
  ไม่มีซอฟต์แวร์ใดในโลกที่สมบูรณ์แบบและทำงานได้ยอดเยี่ยมไปเสียหมดทุกกระบวนการ โครงการดิจิทัลระดับแนวหน้ามักเลือกใช้เครื่องมือที่ "ดีที่สุดในแต่ละงาน" (Best-in-class) 
  ตัวอย่างเช่น ทีมงานอาจจะเลือกใช้ระบบหนึ่งในการครอบตัดรูปภาพและปรับสมดุลแสง (Binarization/Deskewing) แล้วใช้ Kraken ทำการตีกรอบบรรทัดข้อความ (Segmentation) ซึ่งอาจได้ผลลัพธ์ออกเป็น ALTO XML ทว่าในกระบวนการอ่านข้อความด้วย AI กลับเลือกใช้เครื่องมือออฟไลน์อีกตัวที่กินไฟน้อยกว่าแต่ต้องรับอินพุตเป็น PAGE XML ด้วยเหตุนี้ การสับเปลี่ยนฟอร์แมตข้ามไปข้ามมาระหว่างทางจึงต้องอาศัยตัวแปลงข้อมูลที่มีประสิทธิภาพสูงและเสถียรที่สุด เพื่อมิให้สะดุดกลางทาง

### ความเสี่ยงของการแปลง (Risks of Conversion)

การแปลงรูปแบบ XML เป็นความท้าทายเชิงเทคนิคอย่างยิ่ง เนื่องจากทั้ง PAGE และ ALTO ถูกออกแบบมาด้วยหลักปรัชญาที่ต่างกัน (PAGE เกิดมาจากฝั่ง Computer Vision และ HTR ส่วน ALTO เกิดมาจากฝั่งห้องสมุดและการจัดทำแคตตาล็อกเชิงโครงสร้าง) การแปลงข้อมูลอย่างไม่ระมัดระวังอาจทำให้เกิดความเสี่ยงระดับวิกฤตได้:

> [!WARNING]
> **ความเสี่ยงสำคัญระหว่างการแปลง (Critical Conversion Risks)**
>
> 1. **ข้อมูลระดับความมั่นใจของ AI สูตรหาย (Loss of Confidence Scores):**
>    ในกระบวนการ HTR ข้อมูลความมั่นใจ (Confidence Value) ช่วยให้มนุษย์ตัดสินใจว่าคำใดควรตรวจสอบซ้ำ เครื่องมือแปลงหลายตัวไม่ได้ลอกค่า `conf` จาก PAGE ไปเป็น `WC` (Word Confidence) หรือ `CC` (Character Confidence) ใน ALTO ทำให้ข้อมูลส่วนนี้ที่ถูกประมวลผลมาอย่างยากลำบากสูญหายไปในพริบตา
>
> 2. **ความแม่นยำเชิงพื้นที่ลดลงอย่างมีนัยสำคัญ (Degradation of Spatial Accuracy):**
>    การแปลงจากเส้นขอบรูปหลายเหลี่ยมที่โอบล้อมข้อความแนบสนิท (Polygons) ใน PAGE XML ให้กลายมาเป็นกรอบสี่เหลี่ยมจัตุรัสแบบดั้งเดิม (Bounding Boxes) ใน ALTO XML รุ่นที่ยังไม่รองรับเส้นโค้ง ทำให้เสียความแม่นยำทางพื้นที่ เกิดอาการ "Text Drift" โดยที่พื้นที่ของบรรทัดหนึ่งอาจล้ำเข้าไปในพื้นที่ของบรรทัดข้างเคียง โดยเฉพาะกับต้นฉบับลายมือที่มีการเขียนเอียง
>
> 3. **ลำดับการอ่านบิดเบี้ยว (Reading Order Corruption):**
>    ระบบกำหนดลำดับการอ่านของ PAGE และ ALTO มีโครงสร้างแตกต่างกันโดยสิ้นเชิง PAGE ใช้การอ้างอิง ID ผ่าน Ordered Group ที่ต้นเอกสาร ในขณะที่ ALTO อาศัยลำดับของ Block หากโปรแกรมแปลงไม่สามารถเข้าใจระบบนี้ การแสดงผลข้อความในเอกสารหลายคอลัมน์ (เช่น หนังสือพิมพ์) จะเกิดการอ่านประโยคสลับข้ามคอลัมน์ (Cross-column contamination) ซึ่งทำให้เนื้อหาทางประวัติศาสตร์บิดเบือนไปอย่างสิ้นเชิง
>
> 4. **ความไม่เข้ากันของเวอร์ชัน Schema (Schema Version Mismatch):**
>    การส่งออกข้อมูลจากแพลตฟอร์มหนึ่ง อาจล็อกเวอร์ชันการส่งออกเป็น ALTO v2.0 (เพื่อรองรับระบบคลังข้อมูลที่เก่ากว่า) ในขณะที่โปรแกรมที่รอรับอยู่ปลายทางมีความทันสมัยและเรียกร้อง ALTO v4.4 ความไม่ตรงกันตรงนี้จะทำให้ระบบปลายทางปฏิเสธไฟล์ และรายงานข้อผิดพลาดการ Validate อย่างไม่ปรานีประนอม

## 2. เครื่องมือแปลงแต่ละตัว — รายละเอียด

เพื่อรับมือกับความท้าทายนี้ ชุมชนนักพัฒนาและองค์กรทางวิชาการระดับโลกได้สร้างเครื่องมือหลายตัว ต่อไปนี้คือข้อมูลเจาะลึกของเครื่องมือหลักที่ได้รับการตรวจสอบแล้ว (Verified Data):

### 2.1 ocr-fileformat (เครื่องมือที่ครอบคลุมที่สุด)

**ผู้พัฒนา:** ห้องสมุดมหาวิทยาลัยมันไฮม์ (UB-Mannheim) ประเทศเยอรมนี
**ทิศทางการแปลง (Directions):** แปลงไปมาระหว่างรูปแบบหลักหลายทิศทาง (Multi-format: ALTO ↔ hOCR ↔ PAGE ↔ ABBYY)
**ประเภทอินเทอร์เฟซ (Interface):** CLI (Command Line Interface), Web GUI สำหรับใช้งานผ่านเบราว์เซอร์, และ API API เพื่อการพัฒนาประยุกต์ร่วมกับซอฟต์แวร์อื่น

**คำอธิบายเชิงลึก:**
`ocr-fileformat` เป็นเครื่องมือโอเพนซอร์สที่ครอบคลุมการทำงานกว้างขวางที่สุด มันถูกออกแบบมาให้เป็น "มีดพับสวิส" ของวงการดิจิทัล รองรับการแปลงทั้งขาไปและขากลับระหว่าง ALTO, PAGE, hOCR, และ ABBYY FineReader XML เครื่องมือนี้ได้รับการดูแลรักษาสม่ำเสมอ จึงถือเป็น "ตัวหลัก" ที่ผู้ปฏิบัติงานควรมีติดไว้ในกระบวนการทำงานทุกแห่ง โดยปราศจากข้อกังขา

**วิธีการติดตั้ง (Installation):**
ติดตั้งได้อย่างรวดเร็วในระบบที่มี Python Environment (แนะนำ Python 3.8+):
```bash
# ใช้โปรแกรมจัดการแพ็คเกจ pip
pip install ocr-fileformat
```

**คำสั่งใช้งานที่สำคัญ (Commands):**
```bash
# แปลงไฟล์เดียว: จาก ALTO (input_alto.xml) ไปเป็น PAGE (output_page.xml)
ocr-transform alto page input_alto.xml output_page.xml

# แปลงไฟล์เดียว: จาก PAGE ไปเป็น hOCR
ocr-transform page hocr input_page.xml output_hocr.html

# การประมวลผลแบบกลุ่ม (Batch Processing) สำหรับหน้าเอกสารจำนวนมากด้วย Shell Script
for file in my_dataset/*.xml; do
    echo "กำลังตรวจสอบและทำการแปลงไฟล์: $file"
    ocr-transform page alto "$file" "converted_alto/$(basename "$file")"
done
```

**ตัวอย่างความเปลี่ยนแปลงของอินพุตและเอาต์พุต:**
เมื่อแปลงจาก Bounding Box ของ ALTO กลับไปเป็น Polygon ของ PAGE:
> [!NOTE]
> ระบบของ ocr-fileformat จะทำการคำนวณตำแหน่งพิกัดตั้งต้น `HPOS` และ `VPOS` ควบคู่กับการนำความกว้างและความสูง (`WIDTH`, `HEIGHT`) มาบวกลบกัน เพื่อสร้าง `<Coords points="..."/>` ที่มีพิกัด 4 จุดอย่างแม่นยำ สิ่งนี้ทำให้ไฟล์ PAGE ที่ถูกสร้างใหม่ยังคงผ่านกระบวนการ Validation ได้สมบูรณ์ โดยไม่เกิดปัญหาข้อมูลสูญหายทางโครงสร้าง

### 2.2 page-to-alto (เครื่องมือของ OCR-D)

**ทิศทางการแปลง (Directions):** PAGE → ALTO เท่านั้น
**ภาษาที่ใช้พัฒนา (Language):** Python
**ความเหมาะสม:** จัดการสถานการณ์เฉพาะหน้า (Edge cases) และโครงสร้างแปลกๆ ได้ดี

**คำอธิบายเชิงลึก:**
เป็นโปรเซสเซอร์ (Processor) ย่อยตัวหนึ่งที่รวมอยู่ในชุดเครื่องมือขนาดใหญ่ของ DFG-funded OCR-D Framework จุดเด่นของ `page-to-alto` คือความสามารถในการรับมือกับความยุ่งยากทางโครงสร้างของไฟล์ PAGE XML ที่ถูกสร้างขึ้นจากเครื่องมือของ OCR-D เอง มันถูกเขียนให้เข้าใจกรณีการมี Region ซ้อนทับกัน (Overlapping regions) หรือระดับความซ้อนของ Layout หลายชั้นได้อย่างปลอดภัยและรอบคอบที่สุด โดยจะพยายามแปลโครงสร้างที่ไม่เข้าพวก ให้ลงรอยกับสเปคของ ALTO แบบเนียนที่สุด

**วิธีการติดตั้ง (Installation):**
```bash
# ติดตั้งผ่าน pip โดยใช้ชื่อแพ็กเกจของระบบ OCR-D (ไม่ต้องติดตั้งทั้ง OCR-D core)
pip install ocrd_fileformat_transform
```

**คำสั่งใช้งานที่สำคัญ (Commands):**
```bash
# การใช้งานภายใน workspace ของ OCR-D (ต้องมี METS เป็นตัวเชื่อมโยงแฟ้มข้อมูล)
ocrd-fileformat-transform -I OCR-D-PAGE-DIR -O OCR-D-ALTO-DIR -P from-to "page alto"
```

### 2.3 prima-page-converter (เครื่องมืออย่างเป็นทางการจากผู้สร้าง PAGE)

**ผู้พัฒนา:** PRImA Research Lab (Pattern Recognition & Image Analysis) ณ University of Salford สหราชอาณาจักร
**ทิศทางการแปลง (Directions):** ขาเข้าสู่ PAGE เสมอ (ALTO / hOCR / FineReader → PAGE)
**ภาษาที่ใช้พัฒนา (Language):** Java (CLI)

**คำอธิบายเชิงลึก:**
หากมีคนเขียนตัวแปลงเข้าสู่ PAGE ได้ดีที่สุด ก็ต้องเป็นผู้สร้าง PAGE XML เสียเอง เครื่องมือนี้ถือเป็นมาตรฐานทองคำสำหรับการดึงข้อมูลจากแหล่งอื่นเข้าสู่สภาพแวดล้อมการทำงานของ PAGE นอกจากนี้ยังมีฟีเจอร์สำคัญอย่างยิ่งคือ **ความสามารถในการอัปเกรดเวอร์ชันของ PAGE XML ในตัว** ตัวอย่างเช่น ไฟล์ PAGE ที่ถูกสร้างขึ้นด้วยโครงสร้างเก่าเมื่อปี 2010 สามารถถูกแปลงให้อยู่ในโครงสร้างของ schema ปี 2019 หรือ 2024 ได้อย่างไร้รอยต่อ ลดทอนความยุ่งยากเมื่อต้องการโยกย้ายไฟล์ไปยังระบบใหม่ที่ปิดกั้นโครงสร้างเก่า

**วิธีการติดตั้ง (Installation):**
ผู้ใช้งานจำเป็นต้องมี Java Runtime Environment (JRE) เวอร์ชัน 8 ขึ้นไป จากนั้นให้ดาวน์โหลดไฟล์ `.jar` ต้นฉบับจากเว็บไซต์ของ PRImA หรือที่เก็บข้อมูลอย่างเป็นทางการ

**คำสั่งใช้งานที่สำคัญ (Commands):**
```bash
# แปลง ALTO ให้เป็น PAGE พร้อมบังคับส่งออกเป็นรูปแบบ PAGE
java -jar prima-page-converter.jar \
    -source-file /data/raw_inputs/alto_page01.xml \
    -target-file /data/clean_outputs/page_page01.xml \
    -source-format ALTO \
    -target-format PAGE
```

### 2.4 hocr-to-alto (XSLT Stylesheets)

**ทิศทางการแปลง (Directions):** hOCR → ALTO (รองรับ v2.0 จนถึง v4.0)
**ภาษาที่ใช้พัฒนา (Language):** XSLT 2.0 stylesheets

**คำอธิบายเชิงลึก:**
เครื่องมือนี้ไม่ได้มีสภาพเป็นแอปพลิเคชันแบบสแตนด์อโลน (Standalone Application) แบบตัวอื่นๆ แต่เป็นชุดคำสั่ง (Stylesheets) สำหรับทำ Data Transformation ผ่านกลไก XML ดั้งเดิม รูปแบบนี้มีข้อดีคือมีความเบา (Lightweight) และไม่ต้องพึ่งพาไลบรารีซับซ้อน เหมาะสำหรับโครงการที่ใช้ Tesseract ในการรัน OCR แล้วสร้างผลลัพธ์เป็น hOCR (HTML-based format ที่ฝัง microformats) จากนั้นจึงค่อยแปลงโครงสร้างดังกล่าวเพื่อออกเป็น ALTO สำหรับการจัดเก็บถาวรในขั้นตอนสุดท้าย

**วิธีการติดตั้ง (Installation) และข้อกำหนด (Requirements):**
เนื่องจากสคริปต์นี้เขียนขึ้นด้วยเทคโนโลยี XSLT 2.0 (เพื่อให้ประมวลผลข้อมูลที่ซับซ้อนได้อย่างมีประสิทธิภาพมากขึ้น) จึงทำให้ไม่สามารถใช้ XSLT Processor มาตรฐานที่ติดมากับระบบปฏิบัติการทั่วไป (ซึ่งมักรองรับเพียง XSLT 1.0) ในการแปลรหัสได้ ผู้ใช้ **ต้องดาวน์โหลดและเรียกใช้งาน Saxon-HE** (Saxon Home Edition) ในการเป็นตัวกลางการประมวลผล

**คำสั่งใช้งานที่สำคัญ (Commands):**
```bash
# เรียกใช้ Saxon-HE .jar เพื่อประมวลผลอินพุตด้วยไฟล์ hocr2alto.xsl
java -jar saxon9he.jar -s:input_file.hocr -xsl:hocr2alto.xsl -o:output_file.xml
```

## 3. ปัญหา Interoperability — วิเคราะห์ละเอียด

ปัญหาความเข้ากันไม่ได้ของระบบ (Interoperability Problems) ระหว่างไฟล์รูปแบบต่างๆ ที่ต่างสายพันธุ์ เป็นประเด็นทางวิศวกรรมข้อมูลที่ต้องได้รับการตรวจสอบอย่างใกล้ชิด ความไม่สมบูรณ์แบบในการแปลงสามารถสรุปออกมาได้ในประเด็นหลัก 4 ส่วน ดังนี้:

### 3.1 ปัญหาเชิงโครงสร้างแบบลำดับชั้นเทียบกับแบบแบนราบ (Structural Problems)

- **ความไม่สมมาตรของภูมิภาคข้อความ (PAGE hierarchical regions vs ALTO flat blocks):** 
  ความขัดแย้งที่ใหญ่ที่สุดของสองมาตรฐานนี้อยู่ที่ความลึกของแผนผังต้นไม้ PAGE XML มีการออกแบบสถาปัตยกรรมแบบลำดับชั้นที่ลึกและยืดหยุ่นสูง (Hierarchical) สำหรับพื้นที่เรขาคณิต (`Region`) ตัวอย่างเช่น ภายใน `<TextRegion>` หนึ่งบล็อก สามารถมีองค์ประกอบอื่นๆ ซ้อนกันได้อย่างอิสระ หรือแม้กระทั่งมี `TableRegion` ที่มีเซลล์ย่อยๆ ในอีกระดับ ทว่า ALTO XML แบบดั้งเดิม (โดยเฉพาะก่อนการปรับปรุงใหญ่ในเวอร์ชัน 4.3) มีโครงสร้างบล็อกที่แบนราบ (Flat Blocks) เป็นระนาบเดียวกัน 
  **ผลลัพธ์ของการแปลง:** การแปลงข้ามระบบจะไม่ใช่การจับคู่แบบ 1:1 เสมอไป โครงสร้างบล็อกที่มีความซับซ้อนใน PAGE มักจะถูก "แผ่แบน (Flattened)" ออกเมื่อถูกแปลเป็น ALTO ทำให้สูญเสียข้อมูลความสัมพันธ์ทางอรรถศาสตร์ (Semantic relationships) ระหว่างกิ่งก้าน (Parent-Child) อย่างไม่มีทางดึงคืน

- **การจัดการกับป้ายกำกับและข้อมูลเมตาที่ไม่ได้มาตรฐาน (Custom metadata/labels):** 
  ในเอกสาร PAGE XML ระบบต่างๆ หรือซอฟต์แวร์ HTR ขั้นสูง (เช่น Transkribus) มักใช้เสรีภาพของมาตรฐานในการกำหนด `custom` attribute เอาเองเพื่อเก็บค่าบางอย่างที่ไม่ได้มีในมาตรฐานแต่แรก (เช่น ใส่การเข้ารหัส `custom="structure {type:heading;}"` หรือการระบุรายละเอียดปลีกย่อยของงานชิ้นนั้นๆ) แต่องค์ประกอบอิสระเหล่านี้ไม่มีแท็กเทียบเท่าให้จับคู่อย่างตรงตัวในสเปกของ ALTO 
  **ผลลัพธ์ของการแปลง:** ข้อมูลเฉพาะเจาะจงของแอปพลิเคชันเหล่านี้จะถูกตัวแปลงดรอป (Dropped) และละทิ้งทั้งหมด เสมือนหนึ่งไม่เคยมีอยู่จริง

- **ความไม่สมดุลของชนิดพื้นที่ผิว (Region types ที่ไม่มีอยู่จริง):** 
  PAGE XML มาพร้อมกับคำศัพท์ที่กว้างขวางเพื่อรองรับโจทย์สารพัดรูปแบบ โดยมีทั้ง `<MathsRegion>`, `<MusicRegion>`, `<ChartRegion>`, `<ChemRegion>` และ `<NoiseRegion>` เพื่อรองรับงานวิชาการทางวิทยาศาสตร์หรือดนตรีขั้นสูง แต่ ALTO มุ่งเน้นการจัดเก็บข้อความเพื่อห้องสมุด หรือเอกสารตัวอักษรธรรมดาเป็นหลัก 
  **ผลลัพธ์ของการแปลง:** เมื่อเอกสารโน้ตเพลงที่ถูกวิเคราะห์ด้วย PAGE แปลงเป็น ALTO ตัวแปรประเภทต่างๆ เหล่านี้ มักถูกลดรูปลงเพื่อยัดใส่ไว้ใน `<Illustration>` หรือบล็อกข้อความปกติเท่านั้น ทำให้เครื่องมือที่จะนำข้อมูลไปประมวลผลต่อ (Downstream Processing) เช่น การใช้ AI ช่วยอ่านโน้ตเพลง ไม่สามารถจำแนกความแตกต่างระหว่างภาพประกอบปกติกับหน้ากระดาษที่มีแต่โน้ตดนตรีได้

### 3.2 ปัญหาพิกัดและพื้นที่เรขาคณิต (Coordinates Problems)

- **การรวบข้อมูลเส้นรอบวงมาเป็นสี่เหลี่ยมกรอบ (Polygon → Bounding Box = Text Drift):** 
  PAGE เก็บพิกัดทุกชิ้นส่วนข้อความในลักษณะรูปหลายเหลี่ยมความละเอียดสูง (Polygon) ผ่านแท็กย่อย `<Coords points="x1,y1 x2,y2 x3,y3 ..."/>` ซึ่งข้อดีอันมหาศาลคือโอบล้อมข้อความได้อย่างแม่นยำ แม้ว่าประโยคจะถูกเขียนโค้งงอ หรือเอียงหลบกัน แต่เครื่องมือที่แปลงเป็น ALTO เวอร์ชันเก่าจะยอมรับเฉพาะการคำนวณแบบ Bounding Box โดยจะบังคับให้พิจารณาเพียงจุดสูงสุด (Top), ต่ำสุด (Bottom), ซ้ายสุด (Left), และขวาสุด (Right) ของกลุ่มข้อความนั้น แล้ววาดเป็นรูปสี่เหลี่ยมผืนผ้าธรรมดา 
  **ผลกระทบอย่างร้ายแรง:** กรอบที่ครอบข้อความขนาดใหญ่จะซ้อนทับกันเมื่อนำไปวางในเอกสารต้นฉบับที่มีการเขียนเอียง (Skewed text) หรือบรรทัดที่เบียดเสียดกัน ทำให้เกิดปัญหาที่เรียกว่า Text Drift ระบบ OCR รุ่นถัดไปที่ได้รับกรอบซ้อนทับกันจะสร้างความสับสนและดึงภาพตัวอักษรผิดพลาด

> [!CAUTION]
> **ภาพจำลองปัญหา Bounding Box vs Polygon Loss อย่างละเอียด**
>
> สมมติว่ามีบรรทัดอักษรเขียนด้วยลายมือเอียง 45 องศา และบรรทัดอยู่ค่อนข้างชิดกัน:
> **ไฟล์ต้นฉบับ (PAGE XML Polygon)**
> รักษาความเอียงด้วยมุม 4 จุดที่ไม่เป็นมุมฉาก ประหยัดพื้นที่ และรัดกุมรอบตัวอักษร:
> ```xml
> <Coords points="100,200 300,100 310,120 110,220" />
> ```
> 
> **ไฟล์ที่ถูกแปลง (ALTO XML Bounding Box ในสถาปัตยกรรมเก่า)**
> โปรแกรมแปลงจะหาค่า Min/Max ของแกน X, Y สูญเสียความเอียงทั้งหมด บังคับกลายเป็นสี่เหลี่ยมผืนผ้าขนาดใหญ่ที่มุมขนานกับระนาบ:
> ```xml
> <TextBlock HPOS="100" VPOS="100" WIDTH="210" HEIGHT="120">
> ```
> ผลลัพธ์: จะเห็นได้ว่าพื้นที่ที่ถูกกินเพิ่มเข้ามา ทำให้มีโอกาสที่จะดูดกลืนภาพตัวอักษรจากบรรทัดอื่นไปผสมด้วยสูงมาก ซึ่งจะทำให้โมเดลภาษาและการอ่านข้อความล้มเหลวโดยสมบูรณ์

- **ความท้าทายจากมาตราหน่วยวัดที่ต่างกันอย่างรุนแรง:** 
  ALTO มีการกำหนดมาตราวัดความยาวแบบกว้างๆ ในออตทริบิวต์ของแท็ก Description ด้วยแท็ก `<MeasurementUnit>` ซึ่งอาจมีค่าเป็น `pixel` (ที่นิยมที่สุด), `mm10` (1/10 มิลลิเมตร - ซึ่งเหมาะสำหรับการอ้างอิงกับสิ่งพิมพ์จริง), หรือ `inch1200` (1/1200 นิ้ว - สำหรับงานพิมพ์ความละเอียดสูง) 
  ในขณะที่ PAGE ผูกพันกับระบบพิกัด Pixel แบบหน้าจอภาพต้นฉบับเท่านั้น หากโปรแกรมแปลงคำนวณอัตราส่วน DPI ระหว่างหน่วยเมตริกของโลกความเป็นจริงกับค่าพิกเซลผิดพลาด พิกัดของกรอบทั้งหมดบนหน้ากระดาษจะถูกพล็อตตำแหน่งเพี้ยนอย่างรุนแรง อาจหดเล็กลงจนเหลือกระจุกนิดเดียว หรือขยายใหญ่เกินกรอบรูปภาพ ทำให้ข้อมูลชุดนั้นถูกละทิ้งโดยระบบฝึกโมเดลทันที

### 3.3 ปัญหาลำดับการอ่านของเนื้อหา (Reading Order Problems)

- **กลไกที่แตกต่างกันโดยสิ้นเชิง (Divergent Mechanics):** 
  - PAGE XML ใช้กลไกแบบตรรกะที่เด่นชัด (Explicit Order) โดยสร้างแท็ก `<ReadingOrder>` แยกไว้ต่างหาก และใช้แท็ก `<OrderedGroup>` ผสมกับ `<UnorderedGroup>` อ้างอิงด้วย ID ข้ามไปยัง Region ต่างๆ ได้อิสระ โครงสร้างนี้เหมือนแผนที่นำทางที่มีเส้นโยงอย่างชัดเจน
  - ALTO XML (ในยุคก่อนการเปลี่ยนแปลงครั้งใหญ่) ใช้วิธี **Hierarchical Nesting** แบบง่ายๆ คือลำดับการอ่านจะเป็นไปตามการเรียงตัวของโค้ดบรรทัดและบล็อกจากบนลงล่างของไฟล์ XML เอง (เพิ่งเริ่มปรับมาใช้ ReadingOrder Element จริงจังในเวอร์ชัน v4.3 ซึ่งก็ยังมีเครื่องมืออีกนับสิบตัวที่ไม่อัปเดตตาม)
- **การปนเปื้อนข้ามคอลัมน์ในหน้าเอกสารซับซ้อน (Multi-column document contamination):** 
  เมื่อทำการแปลงไฟล์จาก PAGE ไปสู่ ALTO หากสคริปต์ที่ใช้ไม่ได้ทำความเข้าใจโครงสร้างเชิงพื้นที่ของหน้ากระดาษให้ดี (เช่น เป็นบทความในหนังสือพิมพ์ที่มี 3 คอลัมน์) บรรทัดที่ 1 ของคอลัมน์ A อาจถูกต่อท้ายด้วยบรรทัดที่ 1 ของคอลัมน์ B ทันที แทนที่จะไปอ่านบรรทัดที่ 2 ของคอลัมน์ A ทำให้ผู้ใช้, นักประวัติศาสตร์, หรือเครื่องมือประมวลผลภาษาธรรมชาติ (NLP) ที่ต้องใช้งานในภายหลัง อ่านข้อความได้สับสนและไร้ความหมาย

### 3.4 ปัญหาข้อมูลสูญหายอื่นๆ (Data Loss Issues)

- **ความเชื่อมั่นของเครื่องจักรถูกตัดทอน (Confidence Scores Drops):** 
  คะแนนระบุความมั่นใจของแบบจำลอง AI หรือ OCR Engine ที่สร้างข้อความ (มีค่าระดับ 0.0 ถึง 1.0) ในไฟล์ PAGE จะถูกบรรจุอยู่ใน `conf` attribute ของ `TextEquiv` ข้อมูลเชิงสถิตินี้มักตกหล่นหายไปในอากาศระหว่างกระบวนการแปลงหากนักพัฒนาโปรแกรมไม่ได้เจตนาเขียนแผนที่พารามิเตอร์ ให้แปลงค่าจากแบบเก่าเข้าไปอยู่ใน Attributes `WC` (Word Confidence) หรือ `CC` (Character Confidence) ของฝั่ง ALTO
- **รายละเอียดความงดงามและแบบอักษรไม่คงอยู่ (Font and Typographical style failure):** 
  ALTO โดดเด่นอย่างมหาศาลในการเก็บข้อมูลฟอนต์ รูปลักษณ์ ความหนา ความเอียง ผ่านระบบ `<Styles>` อันซับซ้อน แต่ในทางตรงกันข้าม PAGE สนใจแค่ตัวพิมพ์ข้อความธรรมดา (Plain text) และโครงร่างเรขาคณิตของการรับรู้รูปแบบ เมื่อสถาบันพยายามแปลง ALTO ที่มีคุณค่าเหล่านี้ให้กลายเป็น PAGE ข้อมูลความประณีตของตัวอักษร (Typography) มักจะหายไปทั้งหมดอย่างหลีกเลี่ยงไม่ได้
- **การปฏิเสธไฟล์ข้ามเวอร์ชันอย่างรุนแรง (Schema Version Mismatch Fatal Error):** 
  ตัวอย่างที่พบได้บ่อยในหมู่นักวิจัย เช่น โครงการดึงข้อมูลจากแพลตฟอร์ม Transkribus ซึ่งระบบตั้งค่าให้ส่งออกไฟล์เป็นมาตรฐาน ALTO v2 แต่จากนั้นนำไฟล์คอลัมน์ที่ว่า ไปเข้าสู่โปรแกรม eScriptorium ซึ่งมีระบบคัดกรองเข้มงวดและต้องการ ALTO v4.4 เท่านั้น เพราะต้องการใช้ฟีเจอร์บางอย่าง ระบบจะแจ้งเตือน Validation Error ทันทีและไม่อนุญาตให้ผู้วิจัยทำงานต่อ กระบวนการทำงานที่น่าจะราบรื่นจึงชะงักงัน

## 4. ตาราง: ข้อมูลที่สูญหายเมื่อแปลง

การเปรียบเทียบเชิงวิเคราะห์ต่อไปนี้ เป็นตารางสรุปสภาพการณ์ของชิ้นส่วนข้อมูลสำคัญ เมื่อถูกโอนถ่ายข้ามระหว่างรูปแบบทั้งสอง ทิศทางใดมีความเสี่ยงสูญหาย และทิศทางใดสามารถรักษาโครงสร้างเดิมไว้ได้มากที่สุด:

| องค์ประกอบ/แอตทริบิวต์ (Element/Attribute) | การแปลง PAGE → ALTO (ผลลัพธ์ที่ได้) | การแปลง ALTO → PAGE (ผลลัพธ์ที่ได้) |
|:-------------------------------------------|:-----------------------------|:-----------------------------|
| **Region Types เฉพาะทาง** (เช่น `<MathsRegion>`, `<ChemRegion>`, `<MusicRegion>`) | **สูญหาย:** เนื่องจาก ALTO ไม่มีแท็กเฉพาะเหล่านั้น จึงมักถูกตีขลุมให้กลายเป็น `<Illustration>` ธรรมดา สูญเสียคุณสมบัติเชิงความหมายไปโดยสิ้นเชิง | ไม่ได้รับผลกระทบ |
| **ข้อมูลที่ผู้ใช้ปรับแต่งเอง (Custom Metadata/Tags)** | **เสี่ยงสูงมาก:** ข้อมูลเฉพาะระบบที่ซ่อนอยู่ใน `custom` attribute ของ PAGE มักถูกปัดตกทิ้ง เพราะไม่ตรงกับ Schema ที่เข้มงวดของ ALTO | ไม่ได้รับผลกระทบมากนัก แต่อาจแสดงผลเพี้ยน |
| **คะแนนความแม่นยำรายบรรทัด/รายคำ (Confidence Score `conf`)** | เสี่ยง: หากผู้พัฒนาไม่ Map ข้อมูลไปยัง `WC`/`CC` ในฝั่ง ALTO อย่างถูกต้อง ข้อมูลการวินิจฉัยของ AI จะหายวับไป | ส่วนใหญ่คงอยู่ (หากใช้ตัวแปลงอย่างเป็นทางการที่ถูกวิธี) |
| **สไตล์ของฟอนต์ตัวอักษร (`<Styles>`, TextStyle)** | ไม่ได้รับผลกระทบ | **สูญหาย:** PAGE ไม่มีแท็กที่รองรับแบบแผน TextStyle/ParagraphStyle อย่างเป็นระบบละเอียดเท่า ALTO |
| **ข้อมูลความละเอียดของรูปหลายเหลี่ยม (Polygon Coords)** | เสี่ยงสูง: หากแปลงเป็น ALTO เวอร์ชันเก่าที่จำกัด จะถูกรีดแบนให้กลายเป็นสี่เหลี่ยม (Bounding Box - `HPOS`, `VPOS`) สูญเสียรูปทรงโค้งงอและการโอบรัดที่แนบแน่น | คงอยู่: สถาปัตยกรรมของ PAGE ถูกสร้างมาเพื่อให้สามารถอ้าแขนรับ Polygon ได้เป็นมาตรฐานตั้งแต่เกิด |
| **โครงสร้างลำดับการอ่านที่ซับซ้อน (ReadingOrder Structure)** | เสี่ยง: ความซับซ้อนของการอ้างอิง ID ผ่าน Ordered Group ใน PAGE อาจสับสนและเละเทะ เมื่อพยายามเปลี่ยนเป็นลำดับการอ่านด้วยตำแหน่งบรรทัดใน ALTO | มักคงอยู่ แต่อาจขาดรายละเอียดเรื่อง Hierarchical Nesting ของบล็อกเชิงโครงสร้างระดับลึก |
| **เลเยอร์และความสัมพันธ์ข้ามภูมิภาค (Layers / Relations)** | **สูญหาย:** โครงสร้างความสัมพันธ์ข้าม Region ที่ซับซ้อนใน PAGE ไม่สามารถแมปลงในระนาบที่แบนราบของ ALTO ได้โดยตรงอย่างมีประสิทธิภาพ | ไม่ได้รับผลกระทบ |

## 5. Best Practices สำหรับ Format Conversion

ในการดำเนินงานระดับโปรเจกต์ขนาดใหญ่ การสูญเสียข้อมูลหรือข้อมูลถูกบิดเบือนระหว่างการแปลงเพียง 1% ของหน้าหนังสือ 1 แสนหน้า ก็อาจหมายถึงข้อผิดพลาดนับล้านแห่งที่ตามมาหลอกหลอนในภายหลัง เพื่อหลีกเลี่ยงสถานการณ์ที่เป็นฝันร้ายนี้ ขอแนะนำให้บรรณารักษ์และวิศวกรข้อมูล ยึดมั่น "กลยุทธ์ 5 ข้อ" ที่จะช่วยให้การทำงานมีความปลอดภัยสูงสุด:

> [!TIP]
> **กลยุทธ์ 5 ข้อ เพื่อการแปลงรูปแบบที่ปลอดภัยที่สุด (The 5 Safe-Conversion Strategies)**
>
> 1. **ตรวจสอบความบริสุทธิ์ของ Schema ต้นฉบับเสมอ (Validate First):**
>    การนำไฟล์ที่พัง (Corrupted files) ไปแปลงต่อ จะได้ผลลัพธ์ที่พังยิ่งกว่าเดิมเสมอ ใช้เครื่องมือตรวจสอบโครงสร้างทางไวยากรณ์ (Syntax) เช่น `xmllint` เพื่อเช็คให้มั่นใจว่าไฟล์ XML ต้นทางมีความถูกต้องสมบูรณ์ 100% ตามระเบียบของ Schema ปัจจุบัน ก่อนนำเข้าซอฟต์แวร์แปลงไฟล์
>
> 2. **เลือกเครื่องมือที่ได้รับการอัปเดตสม่ำเสมอ (Use Up-to-date and Maintained Tools):**
>    มาตรฐาน XML มีการออกรุ่นใหม่ต่อเนื่อง (เช่น ALTO v4.4 ล่าสุดเมษายน 2023) โปรดหลีกเลี่ยงการใช้ชุดสคริปต์เก่าตามบอร์ดเสวนาหรือโค้ดบน GitHub ที่นักพัฒนาเปิดทิ้งร้างและไม่ได้อัปเดตมาเกิน 3-5 ปี แนะนำให้ตั้งต้นพิจารณาที่ชุดซอฟต์แวร์ที่มีชุมชนดูแลอย่าง `ocr-fileformat` เสมอ
>
> 3. **ทำบททดสอบแปลงไปและกลับอย่างเข้มข้น (Test Round-Trip Transformation):**
>    ก่อนที่จะสับสวิตช์ประมวลผลเอกสารทั้งระบบ (Batch Process) ให้สุ่มดึงเอกสารที่มีโครงสร้างหน้าจอซับซ้อนที่สุดของโครงการมา 5-10 ตัวอย่าง ลองแปลงพวกมันจาก PAGE → ALTO แล้วจึงแปลงไฟล์ผลลัพธ์ตัวนั้นจาก ALTO → PAGE อีกรอบหนึ่ง (Round-trip). ถ้านำไฟล์สุดท้ายมาเทียบกับไฟล์ดั้งเดิมแล้วพบส่วนเบี่ยงเบนหรือความผิดเพี้ยนเกินกว่าที่ยอมรับได้ แสดงว่าเครื่องมือนั้นยังไม่ตอบโจทย์ข้อมูลที่แท้จริงของคุณ
>
> 4. **สำรองข้อมูลต้นฉบับอย่างเคร่งครัดและป้องกันการเขียนทับ (Immutable Original Backup):**
>    ห้ามเขียนทับไฟล์เดิม (Overwrite) เด็ดขาด ไม่มีการรับประกันจากเครื่องมือใดๆ ว่าข้อมูลทั้งหมดจะไม่สูญหาย ให้สร้างโฟลเดอร์สำหรับผลลัพธ์ของการส่งออกโดยเฉพาะแยกจากกันอย่างชัดเจน และถือว่าไฟล์ใหม่นี้เป็นเพียงก้อนข้อมูลชั่วคราวสำหรับป้อนให้ระบบดาวน์สตรีม (Downstream systems) เท่านั้น
>
> 5. **กำหนด Version เป้าหมายให้ชัดเจนตั้งแต่เริ่มโปรเจกต์ (Define Target Versions Early in the Lifecycle):**
>    ข้อผิดพลาดจากปัญหา Mismatch มักเกิดจากการประสานงานและการสื่อสารที่ไม่เคลียร์ หากผู้ว่าจ้างหรือคลังเก็บข้อมูลห้องสมุดร้องขอเป็น ALTO ผู้นำโครงการต้องสอบถามเจาะจงลงไปจนถึงเลขเวอร์ชัน (เช่น เจาะจงขอ v3.0 หรือ v4.4) เพื่อเตรียมตัวตั้งค่าพารามิเตอร์การทำงานของโปรแกรมให้ดึง Schema รุ่นที่ตรงกันเป๊ะที่สุดมาใช้งานได้อย่างราบรื่น

### เช็คลิสต์ตรวจสอบก่อนและหลังการแปลงระบบ (Pre/Post-Conversion Quality Checklist)

เพื่อให้ขั้นตอนการควบคุมประกันคุณภาพ (QA - Quality Assurance) ดำเนินการได้อย่างเป็นระบบ นี่คือรายการตรวจสอบแบบเช็คลิสต์ที่สามารถส่งต่อให้เจ้าหน้าที่ในองค์กรดำเนินการตามมาตรฐาน:

**ก่อนดำเนินการ (Pre-Conversion Audit):**
- [ ] สถิติต้นฉบับ: ไฟล์ต้นฉบับทั้งหมดถูกจัดทำด้วยเครื่องมือ หรือซอฟต์แวร์ยี่ห้อใด (เวอร์ชันอะไร)? (การรู้ที่มาและร่องรอยการเกิดของไฟล์ ช่วยให้คาดการณ์ความเฉพาะทางของแท็กหรือนิสัยซ่อนเร้นได้)
- [ ] เวอร์ชันเป้าหมาย: รุ่น (Version) ของ Schema ของต้นทางและปลายทางที่กำหนดโดยลูกค้าหรือระเบียบโครงการ เป็นรุ่นใดกันแน่? มีการรับรองยืนยันเป็นลายลักษณ์อักษรแล้วหรือยัง?
- [ ] ระดับความแม่นยำ: ข้อมูลพิกัด Polygon มีความสำคัญต่องานชิ้นนี้หรือไม่? (ถ้าใช่: ห้ามใช้เด็ดขาดกับโปรแกรมแปลผลรุ่นเก่าที่บีบบังคับแปลงสภาพให้กลายเป็นกรอบสี่เหลี่ยม Bounding Box ทื่อๆ)
- [ ] ความปลอดภัยของข้อมูล: ไฟล์ดิบทั้งหมดได้รับการ Back up สำรองไปยังสถานที่ปลอดภัย เช่น คลาวด์หรือไดรฟ์แยกต่างหาก และมีการล็อกสิทธิ์ใช้งานเป็นแบบอ่านเท่านั้น (Read-only) แล้วหรือไม่?

**หลังดำเนินการเสร็จสิ้น (Post-Conversion Validation):**
- [ ] ไวยากรณ์ไร้ที่ติ: ได้ทำการสุ่มเปิดไฟล์ผลลัพธ์ปลายทางด้วยเครื่องมือ Validation และยืนยันผลว่าไม่พบรหัสความผิดพลาด (Error Code) ที่ฟ้องถึงการฝ่าฝืนโครงสร้าง XML เลยแม้แต่บรรทัดเดียว?
- [ ] ความลื่นไหลในการอ่าน: ลำดับการอ่าน (Reading Order) ยังคงดำเนินเป็นลำดับที่ถูกต้องตามตรรกะของมนุษย์หรือไม่ เมื่อทดลองสุ่มอ่านจากมุมมองของซอฟต์แวร์ Viewer ตัวสุดท้ายของระบบ?
- [ ] การเชื่อมโยงองค์ประกอบ: ข้อมูลเมตาดาต้าทั้งหมด (เช่น ชื่อไฟล์รูปภาพประกอบ, ขนาดภาพพิกเซลในหน้ากระดาษ, รหัสระบุภาษาหลักของเอกสาร) ยังคงเชื่อมโยงร้อยรัดเข้าด้วยกันอย่างถูกต้องสมบูรณ์หรือไม่?
- [ ] รูปทรงไม่ถูกทำลาย: ตรวจสอบพื้นที่ที่เคยมีการเขียนตัวหนังสือด้วยลายมือที่เอียงคดเคี้ยว (Skewed lines) ว่ามันโดนหั่นเนื้อความ หรือถูกตัดทับบางส่วนจากอิทธิพลของกล่อง Bounding box ที่สร้างขึ้นมาใหม่แบบลวกๆ หรือไม่?

## 6. วิธีเขียน Custom XSLT

ในโลกอุดมคติของนักพัฒนาระบบ โปรแกรมสำเร็จรูปที่มาจากนักพัฒนาใหญ่ๆ ควรตอบสนองความต้องการได้ครอบคลุม อย่างไรก็ตาม ในบริบทของการทำงานโครงการเฉพาะทาง บางครั้งโปรแกรมแปลงรูปแบบทั่วไปไม่อาจหลีกเลี่ยงข้อจำกัดบางประการได้ การสร้างตัวแปลงตามความต้องการเฉพาะ (Custom Converter) โดยอาศัยเครื่องมือดั้งเดิมของชาว XML จึงเป็นทางออกสุดท้ายที่ผู้เชี่ยวชาญระดับสูงเลือกใช้ในการฝ่าฟันอุปสรรค

### XSLT คืออะไร?

**XSLT (eXtensible Stylesheet Language Transformations)** เป็นมาตรฐานสากลและภาษาเขียนโปรแกรมเชิงพรรณนา (Declarative language) ควบคุมโดย W3C ซึ่งใช้สำหรับการแปลงโครงสร้างของเอกสาร XML ชนิดหนึ่ง ไปเป็นเอกสาร XML อีกชนิดหนึ่งได้อย่างมีระเบียบแบบแผน 

หลักการทำงานของ XSLT แตกต่างจากภาษาเชิงคำสั่งตามขั้นตอนแบบปกติอย่าง Python หรือ Java มันเปรียบเสมือนการสร้าง "แม่พิมพ์" และชุดของกฎระเบียบ (Templates) เพื่อทำการเปรียบเทียบลวดลาย (Pattern Matching) ระบบจะสแกนไฟล์เอกสารต้นทางทีละบรรทัดจากบนลงล่าง เมื่อระบบพบโครงสร้างที่บังเอิญตรงตามเงื่อนไข กฎที่ผู้เขียนประกาศไว้จะดักจับองค์ประกอบนั้น จากนั้นบังคับให้ส่งข้อมูลผลลัพธ์ที่มีหน้าตาใหม่และจัดโครงสร้างในรูปแบบใหม่ทั้งหมด ส่งไปยังไฟล์เอาต์พุตปลายทางอย่างเที่ยงตรง

### เมื่อไรควรเขียน Custom XSLT (ทำเอง) vs เมื่อไรควรใช้เครื่องมือสำเร็จ (Ready-made)

**ควรปันใจใช้เครื่องมือสำเร็จรูประดับอุตสาหกรรม (Ready-made Tools) อย่างเช่น ocr-fileformat เมื่อ:**
- เอกสารชุดที่จะแปลงเป็นมาตรฐานธรรมดาทั่วๆ ไป ตามที่กำหนดไว้แต่ดั้งเดิม ไม่ได้มีการแอบอ้างหรือดัดแปลงเพิ่มแท็กที่แปลกประหลาดเกินสเปค
- ทีมงานต้องการประสิทธิภาพและความรวดเร็ว ใช้เวลาเพียงไม่กี่ชั่วโมงในการเซ็ตอัปเข้ากับท่อส่งข้อมูลอัตโนมัติ (Pipeline) และปล่อยให้สคริปต์ทำงานข้ามคืน
- องค์ประกอบในทีมงานไม่มีความพร้อมหรือไม่มีผู้เชี่ยวชาญด้านวิศวกรรมข้อมูล หรือผู้ที่มีความรู้ด้านภาษา XML/XSLT แบบเจาะลึก

**ควรลงทุนลงแรงอย่างหนักเพื่อเขียน Custom XSLT (สร้างขึ้นเอง) เมื่อ:**
- โครงการจำเป็นต้องพึ่งพิงและอ้างอิงกับ **Custom Attribute** เฉพาะทางเยอะมาก ตัวอย่างที่เด่นชัดคือ การทำป้ายกำกับพิเศษ (Labels) ของ eScriptorium เพื่อวิเคราะห์เชิงความหมาย (Semantic structure) ซึ่งเครื่องมือทั่วไปที่ถูกเขียนมากลางๆ จะมองข้ามและลบทิ้งไปดื้อๆ
- ซอฟต์แวร์สำเร็จรูปที่โหลดมา สร้างผลลัพธ์ในลักษณะที่ยังขัดข้องและไม่สามารถทำงานร่วมกับระบบภายในขององค์กรที่ปิดทึบได้ (เช่น องค์กรของรัฐบาลมีการใช้ Namespace ส่วนตัวเพิ่มเติมเข้ามาในข้อกำหนด)
- ทีมวิศวกรมีบุคลากรที่มีความเข้าใจโครงสร้าง Schema เชิงลึกของทั้ง PAGE และ ALTO อย่างทะลุปรุโปร่ง และกระหายที่จะควบคุมกระบวนการดึง ปรับแต่ง และประกอบร่างข้อมูลทุกฝีเข็มด้วยตนเอง

### ตัวอย่าง XSLT Stylesheet สำหรับ ALTO → PAGE (รูปแบบอย่างง่าย เพื่อการสาธิต)

เพื่อทำความเข้าใจและเห็นภาพเชิงสถาปัตยกรรม นี่คือสคริปต์ XSLT เชิงสาธิตฉบับย่อและอ่านง่าย ที่แสดงแนวทางการเขียนคำสั่งดึงข้อมูลจากไฟล์ `ALTO` รุ่นเก่า ที่มีเพียงพื้นที่ทรงสี่เหลี่ยม (Bounding box ธรรมดา) แล้วทำการเปลี่ยนแปลงโครงสร้างสลายร่างกลับไปเป็นระบบเรขาคณิตแบบมุมโอบล้อม (Polygon แบบ 4 จุดพื้นฐาน) ตามกฎเกณฑ์มาตรฐานของ `PAGE`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<xsl:stylesheet version="2.0" 
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:alto="http://www.loc.gov/standards/alto/ns-v4#"
    xmlns:page="http://schema.primaresearch.org/PAGE/gts/pagecontent/2019-07-15"
    exclude-result-prefixes="alto">

    <!-- ระบุคุณสมบัติทั่วไปของไฟล์เอาต์พุตที่จะส่งออก เพื่อให้โค้ดผลลัพธ์อ่านง่าย (Pretty Print) มีการย่อหน้าบรรทัดชัดเจน -->
    <xsl:output method="xml" encoding="UTF-8" indent="yes" />

    <!-- Rule 1: จุดเริ่มต้นเข้าสู่วงจรการแปลง แมตช์ให้ตรงกับ Root node ของ ALTO และสั่งให้สร้างเปลือกหุ้ม PcGts ใหม่ของ PAGE -->
    <xsl:template match="/alto:alto">
        <!-- ประกาศพื้นที่ทำงานใหม่และระบุตำแหน่งดาวน์โหลด Schema มาตรฐานของ PAGE เอาไว้ตรวจสอบภายหลัง -->
        <page:PcGts xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" 
            xsi:schemaLocation="http://schema.primaresearch.org/PAGE/gts/pagecontent/2019-07-15 http://schema.primaresearch.org/PAGE/gts/pagecontent/2019-07-15/pagecontent.xsd">
            
            <!-- ดึงข้อมูลที่เป็นประโยชน์มาสร้าง Metadata เบื้องต้นสำหรับไฟล์ PAGE ใหม่ -->
            <page:Metadata>
                <page:Creator>Custom In-House XSLT Converter (v1.0)</page:Creator>
                <page:Created>
                    <!-- ทำการค้นหาและดึงข้อมูลจากฐานลึกสุดของโครงสร้าง Description ใน ALTO มาเป็นคำตอบ -->
                    <xsl:value-of select="alto:Description/alto:sourceImageInformation/alto:fileName"/>
                </page:Created>
            </page:Metadata>
            
            <!-- กระจายหน้าที่การประมวลผล ไปให้กฎการสร้างระดับหน้ากระดาษ (Page) ทำงานต่อ -->
            <xsl:apply-templates select="alto:Layout/alto:Page"/>
        </page:PcGts>
    </xsl:template>

    <!-- Rule 2: เมื่อพบแท็ก Page ของ ALTO ให้จัดการในระดับหน้ากระดาษ ดึงคุณสมบัติพื้นฐานและมิติความกว้างยาวมาประกบรวมกัน -->
    <xsl:template match="alto:Page">
        <page:Page imageFilename="{@ID}.jpg" imageWidth="{@WIDTH}" imageHeight="{@HEIGHT}">
            <!-- สั่งให้ระบบเดินหน้าวิ่งลึกลงไปหาบล็อกข้อความทั้งหมดที่มีภายในหน้า เพื่อเข้าสู่กฎต่อไป -->
            <xsl:apply-templates select=".//alto:TextBlock"/>
        </page:Page>
    </xsl:template>

    <!-- Rule 3: เมื่อพบแท็ก TextBlock ให้แปลงโครงสร้างเทียบเท่ากับ TextRegion ในโลกของ PAGE -->
    <xsl:template match="alto:TextBlock">
        <page:TextRegion id="{@ID}">
            <!-- ทำการคำนวณเลขคณิตด้วยค่าจาก Bounding Box สร้างพิกัด Coords เสมือน 4 มุม แบบทวนเข็มนาฬิกา -->
            <page:Coords points="{@HPOS},{@VPOS} {@HPOS + @WIDTH},{@VPOS} {@HPOS + @WIDTH},{@VPOS + @HEIGHT} {@HPOS},{@VPOS + @HEIGHT}"/>
            <!-- ประมวลผลลึกลงไปหาเป้าหมายที่เป็นเส้นบรรทัดย่อย (TextLine) ต่อไป -->
            <xsl:apply-templates select="alto:TextLine"/>
        </page:TextRegion>
    </xsl:template>

    <!-- Rule 4: เมื่อพบแท็ก TextLine ให้จัดการระดับบรรทัด เพื่อกำหนดโครงร่างการพิมพ์และรวบรวมตัวอักษรของ PAGE -->
    <xsl:template match="alto:TextLine">
        <page:TextLine id="{@ID}">
            <!-- สร้างกรอบจำกัดขอบเขตในระดับของบรรทัดเดี่ยวด้วยการคำนวณเช่นเดียวกับบล็อก -->
            <page:Coords points="{@HPOS},{@VPOS} {@HPOS + @WIDTH},{@VPOS} {@HPOS + @WIDTH},{@VPOS + @HEIGHT} {@HPOS},{@VPOS + @HEIGHT}"/>
            
            <!-- การดึงชิ้นส่วนข้อความย่อยระดับ String (คำแต่ละคำ) มาร้อยเรียงกันใน TextEquiv/Unicode ตามสเปกของ PAGE -->
            <page:TextEquiv>
                <page:Unicode>
                    <xsl:for-each select="alto:String">
                        <!-- นำผลลัพธ์มารวมกันและเติมช่องว่างด้วย if ถ้าไม่ใช่คำที่อยู่ตำแหน่งสุดท้ายของบรรทัด -->
                        <xsl:value-of select="@CONTENT"/>
                        <xsl:if test="position() != last()"> </xsl:if>
                    </xsl:for-each>
                </page:Unicode>
            </page:TextEquiv>
        </page:TextLine>
    </xsl:template>

</xsl:stylesheet>
```

> [!IMPORTANT]
> **ข้อพึงระวังและข้อควรจำระดับวิกฤต:** 
> โค้ดต้นแบบด้านบนเป็นเพียงการนำเสนอแนวทางเชิงสถาปัตยกรรมเพื่อชี้ให้เห็นถึงกลไกพื้นฐานของการเปลี่ยนรูปร่างระหว่างสองระบบ ในสถานการณ์เพื่อการผลิตจริง (Production-level environment) การพัฒนาเอกสาร XSLT ที่จะไม่มีข้อบกพร่องใดๆ เลยนั้น มีความซับซ้อนทวีคูณอย่างน่าตกใจ เนื่องจากนักพัฒนาจะต้องควบคุมโครงสร้างเงื่อนไขย่อยอื่นๆ ที่ซุกซ่อนอยู่มากมาย 
>
> เช่น การดักจับและทำแผนที่จับคู่ค่าแบบ `<ReadingOrder>`, การคำนวณสูตรคณิตศาสตร์เพื่อจัดการขอบโค้งของเส้นฐานข้อความ (`BASELINE`), รวมถึงการรวบรวมแกะรอยข้อมูลฟอนต์จากแท็ก `<Styles>` เพื่อส่งต่อไปฝังในฐานะของ Custom Attribute อย่างแนบเนียน ดังนั้นทีมงานควรประเมินงบประมาณด้านเวลาให้ถี่ถ้วน และควรพิจารณาทางเลือกในการสร้างโปรเจกต์ XSLT ขนาดใหญ่ให้เป็น "มาตรการทางเลือกสุดท้าย" หลังจากที่เครื่องมือทั่วไปไม่ตอบโจทย์แล้วเท่านั้น
